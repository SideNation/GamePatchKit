# 최소 구현 룰

코드를 **작성·수정하는 시점**에 상시 적용한다. 요청 범위를 넘는 코드가 들어오는 것을 막는 것이 목적이다.

C#/Unity의 설계 문서 단계는 `csharp-feature-architect` / `unity-feature-architect`가, 추상 원칙은 `karpathy-guidelines`가 담당한다. 이 룰은 언어와 관계없이 **실제 코드를 쓰는 순간**만 본다.

## 1. 요청하지 않았으면 넣지 않는다

아래 8개 범주는 현재 요청과 독립적으로 추가할 수 있는 별도 관심사다. 일반적인 모범 사례, 코드 품질 향상, 운영 편의, 향후 필요 가능성만으로 현재 작업에 포함하지 않는다.

표의 항목은 절대 사용 금지가 아니라 **요청 없이 새로 도입하는 것을 금지**한다는 의미다. 사용자가 명시적으로 요청했거나, 없으면 현재 요청 자체를 구현할 수 없는 경우에만 필요한 최소 범위로 넣는다.

| 범주       | 요청 없이 새로 도입하지 않는 것                               |
| ---------- | ------------------------------------------------------------- |
| 보안       | 암호화, 해싱, 솔팅, 토큰 서명, 난독화, 입력 새니타이즈        |
| 견고성     | 재시도, 백오프, 서킷 브레이커, 타임아웃, 폴백 경로            |
| 성능       | 캐싱, 메모이제이션, 오브젝트 풀, 배치 처리, 지연 로딩         |
| 설정       | 옵션 객체, 환경 변수, feature flag, 상수 외부화               |
| 관측       | 로깅, 메트릭, 트레이싱, 진단 이벤트                           |
| 동시성     | 락, 세마포어, 스레드 안전 래퍼, 불필요한 async 전환           |
| 확장       | 인터페이스, 추상 클래스, 제네릭화, 팩토리, 전략, 이벤트 훅    |
| 방어       | 발생 불가능한 상태의 예외 처리, 습관적 null 체크, 방어적 복사 |

### 범위 판정 순서

1. 사용자 요청이나 참조한 요구사항에 명시됐는가? 명시됐다면 넣는다.
2. 없으면 현재 요청이 컴파일·실행되지 않거나 요구한 결과를 낼 수 없는가? 그렇다면 필요한 최소 범위만 넣는다.
3. 현재 수정하는 코드 경로에 이미 적용되던 장치인가? 제거하거나 우회하지 않고 기존 방식을 유지한다.
4. 위 조건에 해당하지 않는가? 넣지 않는다.

**판단 기준:** 이 항목은 현재 요청 자체의 필수 구성인가, 나중에 독립적으로 추가할 수 있는 별도 관심사인가? 별도 관심사라면 넣지 않는다.

### 미리 준비하지 않는다

별도 관심사를 나중에 추가하기 쉽도록 만들기 위한 인터페이스, 옵션, 훅, 빈 구현, 플레이스홀더, TODO, 사용되지 않는 확장 지점을 미리 만들지 않는다.

### 임의로 정책을 결정하지 않는다

현재 요청을 구현하려면 표의 범주 중 하나에 대한 정책 결정이 반드시 필요하지만 요구사항이 없는 경우, 에이전트가 임의의 방식을 선택하지 않는다. 구현 결과가 달라지는 핵심 결정만 사용자에게 확인한다.

## 2. 구현 예산

기본값이다. 초과하면 항목마다 "요청상 반드시 필요한 이유"를 한 줄 적는다.

- 새 파일 1개, 새 타입 1~2개
- 새 인터페이스·추상화 0개
- 새 의존성 0개
- 새 설정 항목 0개

예산을 맞추기 위해 기존 프로젝트의 파일 구조를 깨거나 서로 다른 책임의 타입을 한 파일에 합치지 않는다. 그런 경우에는 구조를 왜곡하는 대신 예산 초과 이유를 적는다.

## 3. 요청 추적

모든 변경 파일과 변경 묶음은 다음 중 하나로 추적돼야 한다.

- 사용자 요청
- 사용자가 참조한 요구사항 문서
- 현재 작업에 적용되는 명시적 프로젝트 규칙
- 요청한 동작의 컴파일·실행에 불가피한 연결 코드

"더 좋아 보인다", "나중에 필요할 수 있다"는 변경 근거가 아니다. 위 근거로 추적되지 않는 변경은 삭제 대상이다.

## 4. 검증과 자가 검토

### 최소 검증

코드를 추가하지 않고 실행할 수 있는 기존 테스트·빌드·정적 검사가 있으면 변경 범위와 직접 관련된 최소 명령만 실행한다.

새 테스트 코드가 사용자 요청에 명시됐거나, 보고된 버그를 재현하는 데 직접 필요한 경우에는 기존 테스트 구조 안에서 가장 작은 테스트만 추가한다. 검증만을 위해 새 테스트 프레임워크, 의존성, 설정, 공통 테스트 인프라를 도입하지 않는다.

### 중복 판정

기존 구현이 책임과 의미까지 같고 재사용이 변경 범위를 줄이면 재사용한다. 겉모양만 비슷하거나 재사용을 위해 기존 구조를 바꿔야 한다면 공통화를 추가하지 않는다. 요청 전에 존재하던 중복은 별도 요청 없이 정리하지 않는다.

### 자가 검토

- [ ] 1번 표의 8개 범주 중 요청 없이 들어간 것이 있는가?
- [ ] 단일 호출자·단일 구현인데 인터페이스나 추상 계층을 만든 곳이 있는가?
- [ ] 같은 책임과 의미를 가진 기존 구현·상수·데이터가 있는데 새로 만들었는가?
- [ ] 중복 제거를 이유로 요청 범위 밖의 기존 코드를 리팩터링했는가?
- [ ] 200줄인데 50줄로 되는가?
- [ ] 시니어 엔지니어가 "과하다"고 말할 코드인가?

하나라도 걸리면 줄이고 다시 검토한다.

## 5. 별도 관심사는 구현하지 않고 분리한다

현재 요청과 독립적으로 구현할 수 있는 항목은 코드에 넣지 않는다. 구체적인 문제나 비용이 확인된 경우에만 완료 보고 말미에 별도 작업으로 한 줄 제안한다.

```text
별도 작업 제안: 현재 요청에서는 캐시를 추가하지 않았다. 반복 조회 성능이 실제 문제가 되면 별도 작업으로 검토할 수 있다.
```

막연히 필요할 수 있다는 이유로 보안·성능·로깅·확장성 등의 후속 작업을 나열하지 않는다. 사용자가 요청하면 그때 넣는다.

## 예외

다음은 이 룰의 적용 대상이 아니다.

- 사용자가 명시적으로 요청한 경우
- 요구사항 문서·PRD·설계 문서에 명시된 경우
- 현재 수정하는 코드 경로에 이미 적용된 장치를 유지하는 경우
- 현재 작업에 적용되는 명시적 프로젝트 규칙이 있는 경우
