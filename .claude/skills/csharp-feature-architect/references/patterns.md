# 패턴 카탈로그 (참조 전용)

> `csharp-feature-architect` 스킬은 기본적으로 패턴을 사용하지 않는다. 단순 구조가 요구사항을 만족하지 못해 패턴 도입을 **검토**할 때만 이 문서를 참조한다. 적용 여부는 항상 "단순 구조 실패 조건"과 연결되어야 한다.

각 항목은 다음 형식을 따른다.

- **언제 검토하나**: 단순 구조가 막히는 조건.
- **언제 도입하지 않나**: 단일 구현·향후 가능성·도메인다움만으로는 도입 금지.
- **C# 적용 메모**: .NET 관례.

## 행동 패턴

### Strategy

- 언제 검토하나: 동일 인터페이스로 5종 이상 변환·검증·정책 분기가 필요하고, 런타임 또는 설정으로 교체된다.
- 언제 도입하지 않나: 분기 2~3개 — `switch`/메서드로 충분.
- C# 적용 메모: `IXxxStrategy` + DI 키드 등록(`AddKeyedScoped`).

### Chain of Responsibility

- 언제 검토하나: 요청 처리에 다단계 미들웨어가 필요하고 단계가 동적으로 조합된다.
- 언제 도입하지 않나: 고정 순서의 2~3단계 — 메서드 호출 순서로 충분.
- C# 적용 메모: ASP.NET Core 미들웨어 파이프라인이 이미 이 패턴이다. 새로 구현하기 전에 미들웨어로 풀 수 있는지 확인.

### Mediator

- 언제 검토하나: 컨트롤러/엔드포인트가 다수의 핸들러를 호출하고 호출 경로가 복잡해진다.
- 언제 도입하지 않나: 컨트롤러 → 서비스 단일 단계. MediatR 도입은 단순 구조 실패 조건이 명확할 때만.
- C# 적용 메모: MediatR 라이센스/버전 정책 확인.

### Observer / Domain Events

- 언제 검토하나: 한 동작이 N개 부수효과를 트리거하고, 호출자가 부수효과를 몰라야 한다.
- 언제 도입하지 않나: 부수효과 1~2개·정적 — 메서드 호출로 충분.
- C# 적용 메모: `IPublisher<TEvent>` 또는 채널/큐.

## 생성 패턴

### Factory / Factory Method

- 언제 검토하나: 생성 로직이 분기·검증·캐싱을 동반하고 호출자가 그 세부를 몰라야 한다.
- 언제 도입하지 않나: `new X(...)` 한 줄로 충분한 경우.
- C# 적용 메모: 정적 팩토리 메서드(`X.Create(...)`) 우선, 클래스 분리는 마지막.

### Builder

- 언제 검토하나: 옵션 조합이 다수이고, 부분 구성·재사용·불변 객체가 필요.
- 언제 도입하지 않나: 생성자 파라미터 3~5개 — 객체 이니셜라이저 또는 record로 충분.
- C# 적용 메모: `record`/`with` 식으로 대체 가능한지 먼저 확인.

## 구조 패턴

### Adapter

- 언제 검토하나: 외부 SDK 인터페이스가 우리 도메인 시그니처와 다르고, 우리 측 코드가 외부 모양에 오염되는 것을 막아야 한다.
- 언제 도입하지 않나: 호출이 1~2곳 — 호출부에서 변환.
- C# 적용 메모: 외부 SDK 의존 경계를 분리하면 테스트 대역이 자연스럽게 따라온다.

### Decorator

- 언제 검토하나: 로깅·캐싱·재시도·메트릭을 동일 인터페이스 위에 합성해야 하고, 합성 순서가 가변적.
- 언제 도입하지 않나: 단일 책임 추가 — 직접 구현 한 곳에 둠.
- C# 적용 메모: `Scrutor`의 `Decorate` 활용 가능.

### Facade

- 언제 검토하나: 호출자가 다수 하위 컴포넌트를 거치는데, 진입점 단순화가 명확한 가치를 제공한다.
- 언제 도입하지 않나: 진입점 단순화 효과가 미미.
- C# 적용 메모: 단순한 service 클래스가 사실상 facade인 경우가 많다.

## 도메인 / 엔터프라이즈

### Domain Event

- 언제 검토하나: 도메인 모델 안에서 발생한 사실이 다른 bounded context로 전파되어야 한다.
- 언제 도입하지 않나: 단일 컨텍스트·단일 호출 — 직접 메서드 호출.

### Specification

- 언제 검토하나: 동일한 조회 조건이 여러 곳에서 재사용·합성된다.
- 언제 도입하지 않나: 단일 호출자 — LINQ 식 직접 사용.

### Saga / Process Manager

- 언제 검토하나: 결제·재고·알림처럼 트랜잭션 경계를 가로지르는 다단계 흐름과 보상 트랜잭션이 필요.
- 언제 도입하지 않나: 단일 트랜잭션·단일 저장소.
- C# 적용 메모: MassTransit, Wolverine, NServiceBus 등 외부 의존 검토.

### CQRS

- 언제 검토하나: 읽기/쓰기 모델 분리, 별도 읽기 저장소, 또는 쓰기 모델 복잡도가 매우 높음.
- 언제 도입하지 않나: 단순 CRUD — 서비스 + 리포지토리로 충분.

## 검토 절차 요약

1. 단순 구조가 막히는 구체적 조건을 적는다.
2. 후보 패턴을 1~2개로 좁힌다.
3. 각 후보를 "도입하지 않을 이유"로 먼저 검증한다.
4. 그래도 남는 후보만 설계 문서 "적용 패턴과 정당화" 표에 한 줄 정당화와 함께 기록한다.
5. 탈락한 후보는 "도입하지 않은 구조"에 제외 이유와 함께 남긴다.
