# C# Feature Architect

C# / .NET 전용. 코드 작성 전 **합의용 설계 문서**(`docs/design/<feature>-design.md`)를 만든다. 가장 단순한 구조가 기본값이며, 추가 계층·인터페이스·패턴은 단순 구조가 요구사항을 만족하지 못할 때만 도입한다.

스킬 자산:

- 설계 문서 템플릿: [template.md](template.md)
- 패턴 카탈로그 참조: [references/patterns.md](references/patterns.md)

연계 스킬:

- 명명/정렬/시그니처 스타일: `csharp-coding-standards`
- 설계 이후 테스트 작성: `csharp-unit-test`, `csharp-api-test`, `csharp-repository-test`
- 광범위·교차 컨텍스트 설계 요청: `csharp-feature-architect` agent (이 스킬을 그대로 따름)

요구사항이 모호하면 작성 전에 확인 질문을 우선한다.

## 핵심 원칙

1. **단순 구조가 기본값** — 단일 클래스, 단일 서비스, 기존 폴더 배치로 요구사항을 해결할 수 있는지 먼저 검토한다.
2. **구조 예산 제한** — 기본 설계는 패턴 0개, 새 인터페이스 0~2개, 새 폴더 계층 1단계 이하를 목표로 한다. 초과 시 항목마다 "요구사항상 반드시 필요한 이유"를 적는다.
3. **기존 구조 우선** — 새 레이어/feature root를 만들기 전에 기존 namespace, 폴더, DI 등록 위치에 붙일 수 있는지 먼저 확인한다.
4. **단일 사용 추상화 금지** — 단일 구현·단일 호출자·단일 시나리오를 위한 인터페이스, 팩토리, 전략, 옵션 객체는 만들지 않는다. "향후 확장 가능성"만으로 추상화하지 않는다.
5. **패턴은 기본 OFF** — GoF/엔터프라이즈 패턴은 단순 구조가 요구사항을 만족하지 못할 때만 도입한다. 적용 시 "왜 필요한가"를 한 줄로 정당화한다.
6. **도메인 분해는 선택 사항** — 엔티티, 값 객체, 도메인 서비스, 이벤트는 개념이 자연스럽게 존재할 때만 분류한다. 단순 기능은 DTO, service, validator, options, controller/endpoint 같은 평범한 책임 단위를 우선 사용한다.
7. **가정과 모호점 명시** — 요구사항이 불명확하면 확인 질문 우선. 프로젝트 구조가 없으면 일반 .NET 기준으로 가정하고 설계 문서에 기록한다.
8. **agent 사용도 선택 사항** — 단순 설계는 이 스킬 단독으로 처리한다. 요구사항이 크거나 여러 bounded context/프로젝트/레이어를 가로질러야 할 때만 `csharp-feature-architect` agent를 사용한다.

## Procedure

1. **요구사항 수집** — 자연어 요청 또는 참조 문서에서 기능, 입력, 출력, 제약을 추출한다. 모호하면 사용자에게 확인 질문.
2. **프로젝트 컨텍스트 확인** — 기존 C# 프로젝트가 있으면 `.sln`/`.csproj`, 폴더 구조, namespace, DI 등록 방식, 기존 feature/layer 배치와 naming/style을 확인한다. 없으면 일반 .NET 기준으로 가정하고 문서에 기록한다.
3. **실행 방식 판단** — 단순 요청은 이 스킬 단독. 요구사항이 크거나 분석 범위가 넓으면 `csharp-feature-architect` agent가 같은 절차를 따르는 방식으로 사용할 수 있음을 설계 문서 "실행 방식" 섹션에 기록한다.
4. **가장 단순한 구조 후보 작성** — 단일 클래스/단일 서비스/기존 폴더 배치로 해결 가능한 안을 먼저 제안한다.
5. **단순 구조 실패 조건 확인** — 단순 구조가 요구사항을 만족하지 못하는 경우에만 책임 분리·도메인 객체·별도 레이어·패턴 도입을 고려한다. 실패 조건을 설계 문서에 구체적으로 적는다. 실패 조건이 없으면 단순 구조로 확정.
6. **책임/도메인 분해** — 필요한 경우에만 한 책임 = 한 클래스 원칙으로 분해한다. 도메인 개념이 요구사항에서 직접 나오지 않으면 억지로 만들지 않는다.
7. **인터페이스 판단** — 인터페이스는 외부 의존성, 대체 구현, DI 경계, 테스트 대역, 이미 프로젝트에서 관례화된 경계가 있을 때만 만든다.
8. **패턴 판단** — 패턴은 기본 사용 안 함. 정당화가 약하면 패턴을 빼고 단순 클래스로 둔다. 카탈로그가 필요하면 [references/patterns.md](references/patterns.md)를 참조한다.
9. **구조 초안 작성** — 인터페이스·클래스의 이름, 파라미터, 반환 타입, 예외 등 **시그니처만** 작성한다. 메서드 본문은 작성하지 않는다. `csharp-coding-standards` 룰을 따른다.
10. **파일·폴더 배치 제안** — 기존 구조 재사용 우선. 새 구조가 필요하면 Feature 단위(`Features/<FeatureName>/`) 또는 레이어 단위(`Domain/`, `Application/`, `Infrastructure/`) 중 프로젝트에 맞는 한 가지만 선택한다.
11. **도입하지 않은 구조 기록** — 사용하지 않은 패턴·인터페이스·레이어와 제외 이유를 설계 문서에 남긴다.
12. **단순화 자가 검토** — 구조 예산 초과, 도메인 객체 과잉, 단일 구현 인터페이스, 새 폴더 계층 증가 여부를 점검하고 결과를 문서에 남긴다.
13. **위임 안내** — 산출 문서 말미에 구현은 일반 코딩 작업, 테스트는 `csharp-unit-test` / `csharp-api-test` / `csharp-repository-test`로 위임함을 명시한다.
14. **출력 및 보고** — 설계 문서를 `docs/design/<feature>-design.md`(사용자 지정 경로 허용)에 저장하고, 만든 경로 + 핵심 결정(실행 방식, 분리 단위, 적용 패턴 수, 새 인터페이스 수)을 1~3줄로 보고한다.

## 단순화 자가 검토 체크리스트

설계 완료 전 모두 점검:

- [ ] 새 인터페이스 수가 2개 이하인가? 초과 시 항목마다 정당화가 있는가?
- [ ] 새 폴더 계층이 1단계 이하인가? 초과 시 정당화가 있는가?
- [ ] 적용 패턴이 0개인가? 도입했다면 "단순 구조 실패 조건"이 명시돼 있는가?
- [ ] 단일 구현·단일 호출자만 있는 인터페이스를 만든 곳은 없는가?
- [ ] 요구사항에서 직접 도출되지 않은 도메인 객체(Entity/VO/Event)를 추가한 곳은 없는가?
- [ ] 기존 namespace/폴더/DI 등록 위치에 붙일 수 있는데 새 레이어를 만든 곳은 없는가?
- [ ] 향후 확장 가능성만으로 추상화한 곳은 없는가?

하나라도 실패하면 단순 구조로 되돌리거나 정당화를 문서에 추가한다.

## 설계 문서 섹션 구성

[template.md](template.md)와 동기화. 산출 문서는 다음 14개 섹션을 포함한다.

1. 기능 요약 (1~3문장)
2. 가정과 확인 필요 사항
3. 요구사항 정리 (입력 / 출력 / 제약)
4. 실행 방식 (skill 단독 / agent + skill)
5. 가장 단순한 구조 후보
6. 단순 구조 실패 조건 (없으면 "없음")
7. 책임/도메인 분해 (필요한 경우만)
8. 적용 패턴과 정당화 (없으면 "없음")
9. 인터페이스 생성 근거 (없으면 "없음")
10. 인터페이스·클래스 시그니처 (구현 없음)
11. 파일·폴더 배치 제안
12. 도입하지 않은 구조
13. 단순화 자가 검토 결과
14. 위임 다음 단계

## 제약

- C# / .NET 전용. 다른 언어 요청 거절.
- **구현 코드 금지** — 시그니처와 책임 기술까지만 작성한다.
- `csharp-coding-standards` 룰을 참조해 명명·정렬을 맞춘다.
- DI 컨테이너·프레임워크 종속이 생기면 설계 문서에 명시한다.
- 패턴 카탈로그가 필요하면 [references/patterns.md](references/patterns.md)를 참조한다. 본 `SKILL.md`에는 "언제 참조할지"만 둔다.
- `_meta.meta`는 `version`, `updated`, `changelog`를 포함한다. 본문에 SemVer를 적지 않는다.
- 최초 버전은 `0.1.0`.

## Anti-patterns

- 단순 구조 검토 없이 곧바로 레이어/패턴/인터페이스를 도입.
- 단일 구현 인터페이스(`IFooService` + `FooService`)를 "테스트 대역 가능성"만으로 추가.
- 요구사항에 없는 도메인 이벤트/값 객체를 "도메인다움"을 위해 추가.
- 메서드 본문, 알고리즘, 예제 코드를 설계 문서에 작성.
- 한 PRD/요청에서 여러 설계 문서 파일을 동시에 만든다.
- "도입하지 않은 구조"·"단순화 자가 검토" 섹션을 비워둔다.
