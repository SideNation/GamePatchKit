### ✅ 수정/구현: deterministic glob·source snapshot 계약

**배경:** `include`·`exclude`의 glob dialect와 숨김 파일 처리, Core와 Packager의
filesystem 책임 경계가 고정되지 않아 OS·구현체별 파일 선택 결과가 달라질 수 있었다.

**수정:**

- v1 glob을 literal·segment 내부 `*`·완전한 segment `**`만 지원하는 자체 dialect로
  제한하고 `/`, NFC, ordinal case-sensitive matching을 고정했다.
- include OR → exclude 우선 → group matching 순서와 re-include 없음, 숨김 segment의
  명시적 literal `.` 포함 조건을 정의했다.
- editor metadata와 임시 파일의 암묵적 자동 제외를 제거하고 설정의 명시적
  `exclude`로 처리하게 했다.
- Core는 문자열 경로 정규화·glob matching·선택·정렬만 담당하고, Packager는
  symlink·junction·reparse point no-follow 열거와 filesystem 검증을 담당하게 했다.
- Packager가 source identity·크기·수정 시각 snapshot, stream 전후 검증과 최종
  재열거를 수행하고 경합 감지 시 manifest를 만들지 않도록 했다.
- PRD 검증 기준 26과 Schema·Packager·문서화 계획을 연결했다.

  사용**해 대소문자만 다른 경로(OS 독립 충돌 규칙 위반)를 놓쳤다.
  `RelativePathNormalizer.FindCaseInsensitiveDuplicateGroups`를 추가로 적용했다.
- **(High) 하나의 file artifact를 공유하는 file들의 size·fileHash 일관성을
  검증하지 않았다.** 같은 artifactHash를 참조하는 첫 번째 file의 (size,
  fileHash)를 기록해 이후 참조와 다르면 거부하도록 추가했다.
- **(High) bundle entry 1:1 대응 검증이 불완전했다.** 같은 bundle 안에서
  `entries[].path`가 중복돼도(각각 1번씩만 참조되면) 잡지 못했고,
  `files[].path`가 `source.entryPath`와 달라도 통과했다. 둘 다 검사를 추가했다.
- **(Medium) multipart 크기 합계 계산이 `long` overflow에 취약했다.** part 2049개
  (2048개는 `2^53-1`, 1개는 2048 byte, 합계가 정확히 `2^64`)로 실제 재현
  테스트를 만들어, 미수정 상태에서 unchecked 덧셈이 0으로 wrap되어 조작된
  `parts.size: 0`과 우연히 일치해 통과했을 시나리오를 확인했다. 누적 중
  `MaxSafeInteger` 초과 시점에서 즉시 overflow로 표시하고 더 누적하지 않도록
  고쳤다.
- **(Medium) `GlobPattern`이 pattern 문자열을 NFC로 정규화하지 않았다.** NFD로 쓴
  pattern이 `RelativePathNormalizer`로 NFC 정규화된 후보 경로와 매칭에 실패할 수
  있었다. `TryParse`에서 NFC 정규화를 추가했다.
- **(Medium) `CanonicalJsonWriter`가 unpaired UTF-16 surrogate를 `Encoding.UTF8`의
  기본 replacement fallback으로 조용히 치환**해, unpaired surrogate 문자열과
  리터럴 U+FFFD 문자열이 같은 canonical byte(같은 hash)로 충돌할 수 있었다.
  throwing `UTF8Encoding`으로 바꿔 `FormatException`을 던지도록 고쳤다.
- **(Low) golden vector가 전부 ASCII라 JCS(UTF-16 code unit) key 정렬과 domain
  array의 UTF-8 byte 정렬이 실제로 다르다는 걸 증명하지 못했고, golden vector
  생성에 쓴 Python 스크립트도 세션 스크래치패드에만 있어 세션이 끝나면
  사라졌다.** U+1F600(surrogate pair) vs U+E000(단일 code unit)로 두 정렬이
  반대 순서를 만드는 것을 증명하는 테스트를 추가했고, Python 생성·검증
  스크립트를 `tests/fixtures/golden-vectors/tools/`에 커밋했다(`--check`
  옵션으로 커밋된 fixture와 재검증 가능).

모든 수정에 회귀 테스트를 추가했다. `GamePatchKit.Core.Tests`는 107 → 124개로
늘었고 clean rebuild 3회 반복 실행으로 안정성을 확인했다.

### ✅ 수정/구현: 03단계 Core identity·diff·download plan

**배경:** 02가 고정한 schema·canonical 계약 위에서 Packager와 Runtime이 공유할
순수 계산 로직(`docs/plan/03-core-identity-diff-plan.md`)을 구현했다. Core는
여전히 filesystem·HTTP·압축 구현을 참조하지 않는다.

**구현:**

- `Sha256Hash`: 64KiB 고정 버퍼 streaming SHA-256 → lowercase hex64. 1MiB 입력을
  한 번에 요구하지 않는 것을 `RecordingStream`으로 검증한다.
- `ReleaseIdentity`: canonical identity byte, `dataVersion`(`v1-` + hex64),
  canonical manifest byte, `manifestHash`, `Finalize(draft, compactVersion)`,
  그리고 byte ↔ 기대 `manifestHash` 검증 API. `Finalize`는 draft에 기록된
  `dataVersion`을 무시하고 다시 계산한다.
- `CompactVersionRule.Resolve`: candidate를 source `compactVersion`으로
  canonicalize해 byte가 같으면 `Changed=false`로 세 값을 그대로 재사용하고,
  다르면 `dataVersion` 유지 + `compactVersion + 1` + 새 `manifestHash`.
  candidate의 논리 상태가 source와 다르면 `ArgumentException`으로 거부한다.
- `ReleaseDiff`: 논리(`files[]` 기준 Added/Removed/ContentChanged/GroupMoved)와
  물리(저장 object 경로 기준 Added/Removed)를 분리해 각각 경로 순으로 정렬.
- `DownloadPlanner`: 명시적 target group 집합만 계획, 경로+검증된 `fileHash`가
  같으면 재다운로드 없음, bundle은 한 번만, part는 누락분만 + 결합 hash 검증
  요구, 예상 다운로드 byte·임시 공간·파일 수·bundle 수 계산.
- `ICompressionCodec`(async 전용)과 `CompressionCodecIds.Zstd`. Core assembly가
  압축 구현체를 참조하지 않는 것을 `TestAssemblyWiring`에서 확인한다.
- `ManifestArtifact.GetPayloadObjects()`를 추가해 diff·plan이 artifact 단위가
  아니라 실제 저장 object 단위로 동작하게 했다(같은 `artifactHash`의 재분할을
  잡기 위함).

**검증:** `GamePatchKit.Core.Tests` 163개(118 → 163), 전체 solution 171개 통과.
02의 golden vector 4종은 이제 `ReleaseIdentity`를 그대로 통과시켜 재현한다.

### ✅ 수정/구현: 03단계 Codex adversarial review 3건 반영

**배경:** 03 구현 직후 `/codex:adversarial-review`에서 `needs-attention` 3건.
핵심은 하나의 잘못된 가정이었다 — "저장 object는 경로로 유일하게 식별된다".

**원인:** part 경로는 `files/<artifactHash>/part-#####`로, 자기 byte가 아니라
**부모 artifact의 hash**로 주소화된다. 같은 30 byte payload를 20+10에서 16+14로
다시 나누면 `artifactHash`·part 개수·part 경로가 전부 그대로인 채 각 part의
크기와 `partHash`만 바뀐다.

**수정:**

- `DownloadPlanner`가 `IEnumerable<string>` 대신
  `IEnumerable<CachedArtifactObject>`(경로 + `objectHash`)를 받고 둘 다 일치할
  때만 cache hit으로 본다. 이전에는 옛 split의 part를 재사용해 결합 hash가 절대
  맞지 않는 계획을 만들 수 있었다.
- `ReleaseDiff`의 물리 비교 단위를 경로에서 `(경로, objectHash)`로 바꿨다. 같은
  경로에 다른 byte가 오면 Removed + Added 쌍으로 보고한다(정렬 키도 경로 →
  `objectHash`로 확장). 이전에는 재분할을 "물리 변경 없음"으로 봤다.
- `ReleaseIdentity.Finalize`가 draft의 collection을 복사한 뒤 identity를
  계산한다. `ReleaseManifest`가 collection을 참조로 보관하므로, 이전에는 호출자가
  원본 list를 나중에 수정하면 모델과 서명 대상 byte가 서로 다른 release를
  가리킬 수 있었다.
- part 경로 규칙 자체를 바꾸라는 권고는 반영하지 않았다. 02에서 고정한 PRD
  계약이고 schema·golden vector가 이미 그 값에 묶여 있다.

**검증:** Core 166개(163 → 166), 전체 solution 174개 통과. 세 수정을 임시로
되돌려 새 회귀 테스트 3개만 정확히 실패하는 것을 확인했다.
