### ✅ 수정/구현: release 식별 계약 단순화

**배경:** `releaseId` 계산 입력에서 manifest schema version이 빠지면 같은 불변 경로에
서로 다른 manifest byte가 충돌할 수 있었다.

**수정:**

- manifest 내부에는 `manifestHash`를 기록하지 않으며 channel과 Runtime current
  pointer가 `manifestHash`를 보유한다.
- `compactVersion`은 최초 package `0`, incremental 상속, compact 시 `+1`로 정의한다.
- 사용자의 명시적 지시에 따라 PRD는 `개발 v2`를 추가하지 않고 기존 `개발 v1` 본문을
  직접 갱신했다.

### ✅ 수정/구현: optional group과 `PackageState` 계약

**배경:** 최초 plan에서 optional group을 다운로드하지 않으면서도, 전역 release 갱신과
나중의 optional 설치가 어떤 manifest를 기준으로 동작하는지 로컬에 일관되게 기록할
명세가 필요했다.

**수정:**

- 최초 설치와 전역 release 갱신은 required group만 다운로드하고, optional group은 현재
  active manifest를 기준으로 요청 시 별도 설치한다.
- package별 `PackageState` 하나에 전역 active pointer와 group별
  `ready`·`notInstalled`·`stale` 상태를 기록한다.
- 변경되지 않은 optional group은 다운로드 없이 새 active manifest에 재연결하고,
  변경된 optional group은 기존 byte를 보존하되 `stale`로 만들어 노출하지 않는다.
- `PackageState` v1 필드 형식과 불변 조건, opaque `installationKey`, 최초 state 구성,
  writer lock, immutable installation과 원자적 state 교체 순서를 명시했다.
- 손상된 state는 cache 경로만 보고 활성 버전을 추정하지 않으며, host가 제공한 신뢰
  가능한 target pointer를 기준으로만 재구성한다.
- PRD 검증 기준 22·23과 Runtime·DotNet·adapter conformance·문서화 계획을 연결했다.
- 사용자의 명시적 지시에 따라 새 `개발 v2`를 만들지 않고 `개발 v1`을 직접 수정했다.

### ✅ 수정/구현: multi-group activation batch 원자성

**배경:** 여러 group을 한 요청으로 다운로드할 때 group마다 `PackageState`를 commit하면
일부 group만 `ready`인 중간 상태가 노출될 수 있었다.

**수정:**

- 한 Runtime 요청의 target group 집합을 하나의 activation batch로 정의했다.
- group별 다운로드·검증·staging은 병렬로 허용하지만 committed state는 변경하지 않는다.
- 모든 group의 immutable installation 승격 후 `PackageState` 전체를 한 번만 교체하고
  `stateRevision`도 한 번만 증가시킨다.
- 한 group 실패 시 batch 전체가 이전 state를 유지하며, commit 직전
  `active.manifestHash`·`stateRevision` 충돌 시 최신 state 기준으로 재계획한다.
- Runtime·DotNet·adapter conformance에 부분 활성화 방지와 단일 commit 검증을 추가했다.

### ✅ 수정/구현: manifest 계약·canonical golden vector

**배경:** 최상위 manifest 필드와 반복 직렬화 결정성만으로는 file·parts·bundle 구조,
참조 무결성과 서로 다른 구현체의 byte 호환성을 보장할 수 없었다. Adapter conformance의
signed fixture와 서명 구현 단계 사이에도 선행 관계가 맞지 않았다.

**수정:**

- `release-manifest.schema.json`에 file·bundle, single·parts payload와
  file·bundleEntry source의 discriminated union 계약을 추가했다.
- JSON Schema 구조 검증, Core `ManifestValidator` 의미·참조 검증, Packager·Runtime의
  실제 payload byte 검증을 분리했다.
- manifest 내부의 중복·미참조 artifact는 거부하되 공유 저장소의 과거 artifact 파일은
  허용하도록 구분했다.
- RFC 8785 JCS·I-JSON과 domain 배열 정렬, safe integer, hash·base64url encoding을
  고정하고 `manifest-signature.schema.json`을 추가했다.
- single file·multipart file·bundle entry의 공용 golden vector에서 canonical
  identity·manifest byte, `dataVersion`, `manifestHash`와 signature를 고정하도록 했다.
- 10단계는 unsigned conformance, 11단계는 signed extension을 담당하고 12단계는
  `05~11` 이후 실행하도록 의존 관계를 정리했다.
- PRD 검증 기준 25와 Core·Packager·Runtime·conformance·서명 계획을 연결했다.

### ✅ 수정/구현: deterministic glob·source snapshot 계약

**배경:** `include`·`exclude`의 glob dialect와 숨김 파일 처리, Core와 Packager의
filesystem 책임 경계가 고정되지 않아 OS·구현체별 파일 선택 결과가 달라질 수 있었다.

**수정:**

- v1 glob을 literal·segment 내부 `*`·완전한 segment `**`만 지원하는 자체 dialect로
  제한하고 `/`, NFC, ordinal case-sensitive matching을 고정했다.
- include OR → exclude 우선 → group matching 순서와 re-include 없음, 숨김 segment의
  명시적 literal `.` 포함 조건을 정의했다.
- editor metadata와 임시 파일의 암묵적 자동 제외를 제거하고 설정의 명시적
  `exclude`로 처리하게 했다.
- Core는 문자열 경로 정규화·glob matching·선택·정렬만 담당하고, Packager는
  symlink·junction·reparse point no-follow 열거와 filesystem 검증을 담당하게 했다.
- Packager가 source identity·크기·수정 시각 snapshot, stream 전후 검증과 최종
  재열거를 수행하고 경합 감지 시 manifest를 만들지 않도록 했다.
- PRD 검증 기준 26과 Schema·Packager·문서화 계획을 연결했다.

### ✅ 수정/구현: compact no-op·Packager API·서명 rotation·메모리 gate

**배경:** 물리 배치가 같은 compact도 새 manifest를 만들 수 있었고, verify·sign이 CLI
내부 구현으로 굳어질 위험이 있었다. 단일 `manifest.sig`의 rotation 의미와 성능 회귀의
수치 기준도 확정되지 않았다.

**수정:**

- candidate 물리 배치가 source와 같으면 compact를 성공 no-op으로 처리해 기존
  `dataVersion`·`compactVersion`·`manifestHash`를 재사용하고 파일을 만들지 않게 했다.
- Packager에 CLI 독립 streaming verify·sign API와 typed result를 두고 CLI는 키·option·
  출력 adapter만 담당하게 했다.
- `keyId`를 raw Ed25519 public key SHA-256 fingerprint로 고정하고, 기존
  `manifest.sig` 재서명을 금지하며 새 release부터 새 key를 쓰는 rotation 순서를
  정의했다.
- RFC 8032 Section 7.1 known-answer vector와 signature negative test를 완료 기준에
  추가했다.
- Ubuntu 24.04 x64 기준 1GiB fixture peak RSS 512MiB, 256MiB→1GiB 증가 64MiB를
  blocking 성능 gate로 고정했다.
- 기존 검증 기준 9·17·25를 보강하고 새 번호는 추가하지 않았다.
