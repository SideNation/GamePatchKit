### ✅ 수정/구현: deterministic glob·source snapshot 계약

**배경:** `include`·`exclude`의 glob dialect와 숨김 파일 처리, Core와 Packager의
filesystem 책임 경계가 고정되지 않아 OS·구현체별 파일 선택 결과가 달라질 수 있었다.

**수정:**

- v1 glob을 literal·segment 내부 `*`·완전한 segment `**`만 지원하는 자체 dialect로
  제한하고 `/`, NFC, ordinal case-sensitive matching을 고정했다.
- include OR → exclude 우선 → group matching 순서와 re-include 없음, 숨김 segment의
  명시적 literal `.` 포함 조건을 정의했다.
- editor metadata와 임시 파일의 암묵적 자동 제외를 제거하고 설정의 명시적
  `exclude`로 처리하게 했다.
- Core는 문자열 경로 정규화·glob matching·선택·정렬만 담당하고, Packager는
  symlink·junction·reparse point no-follow 열거와 filesystem 검증을 담당하게 했다.
- Packager가 source identity·크기·수정 시각 snapshot, stream 전후 검증과 최종
  재열거를 수행하고 경합 감지 시 manifest를 만들지 않도록 했다.
- PRD 검증 기준 26과 Schema·Packager·문서화 계획을 연결했다.

- **(High) 하나의 file artifact를 공유하는 file들의 size·fileHash 일관성을
  검증하지 않았다.** 같은 artifactHash를 참조하는 첫 번째 file의 (size,
  fileHash)를 기록해 이후 참조와 다르면 거부하도록 추가했다.
- **(High) bundle entry 1:1 대응 검증이 불완전했다.** 같은 bundle 안에서
  `entries[].path`가 중복돼도(각각 1번씩만 참조되면) 잡지 못했고,
  `files[].path`가 `source.entryPath`와 달라도 통과했다. 둘 다 검사를 추가했다.
- **(Medium) multipart 크기 합계 계산이 `long` overflow에 취약했다.** part 2049개
  (2048개는 `2^53-1`, 1개는 2048 byte, 합계가 정확히 `2^64`)로 실제 재현
  테스트를 만들어, 미수정 상태에서 unchecked 덧셈이 0으로 wrap되어 조작된
  `parts.size: 0`과 우연히 일치해 통과했을 시나리오를 확인했다. 누적 중
  `MaxSafeInteger` 초과 시점에서 즉시 overflow로 표시하고 더 누적하지 않도록
  고쳤다.
- **(Medium) `GlobPattern`이 pattern 문자열을 NFC로 정규화하지 않았다.** NFD로 쓴
  pattern이 `RelativePathNormalizer`로 NFC 정규화된 후보 경로와 매칭에 실패할 수
  있었다. `TryParse`에서 NFC 정규화를 추가했다.
- **(Medium) `CanonicalJsonWriter`가 unpaired UTF-16 surrogate를 `Encoding.UTF8`의
  기본 replacement fallback으로 조용히 치환**해, unpaired surrogate 문자열과
  리터럴 U+FFFD 문자열이 같은 canonical byte(같은 hash)로 충돌할 수 있었다.
  throwing `UTF8Encoding`으로 바꿔 `FormatException`을 던지도록 고쳤다.
- **(Low) golden vector가 전부 ASCII라 JCS(UTF-16 code unit) key 정렬과 domain
  array의 UTF-8 byte 정렬이 실제로 다르다는 걸 증명하지 못했고, golden vector
  생성에 쓴 Python 스크립트도 세션 스크래치패드에만 있어 세션이 끝나면
  사라졌다.** U+1F600(surrogate pair) vs U+E000(단일 code unit)로 두 정렬이
  반대 순서를 만드는 것을 증명하는 테스트를 추가했고, Python 생성·검증
  스크립트를 `tests/fixtures/golden-vectors/tools/`에 커밋했다(`--check`
  옵션으로 커밋된 fixture와 재검증 가능).

3. R3: H를 16+14로 재분할 → R2와 공유 경로가 없어 gate 통과, 그러나 아직 남아

### ✅ 수정/구현: zstd malformed·truncated frame 거부

**증상:** `NativeCompressions.Zstandard` 0.6.1의 `ZstandardStream` 해제 경로는
checksum 불일치나 잘못된 frame에서 `InvalidData`를 소비 없이 반복해 hang하고,
frame footer가 잘린 입력은 `NeedMoreData` 상태에서 EOF를 성공으로 반환했다.

**수정:**

- 해제 구현을 `ZstandardStream.CopyToAsync`에서 low-level
  `ZstandardDecoder` loop로 교체했다.
- pool 기반 64KiB 입력·출력 buffer로 streaming을 유지하면서 `InvalidData`,
  decoder 무진행과 frame 완료 전 EOF를 `InvalidDataException`으로 거부한다.
- cancellation은 각 상태 전이와 stream read/write에 전달하고, 성공·실패·취소
  모든 경로에서 pooled buffer를 반환한다.
- 잘못된 magic, checksum 1-byte 변조, 빈 압축 stream, 정상 frame의 마지막
  1~4 byte 절단을 회귀 테스트로 고정했다. 2MiB round-trip은 압축 입력을 13-byte
  chunk로 읽혀 `NeedMoreData`와 `DestinationTooSmall` 전이를 함께 검증한다.
- codec 사용 문서의 예외·부분 출력 폐기 계약과 04 계획의 `개발 v2` 완료 상태를
  갱신했다.

**검증:** 수정 전 truncated test 4개가 모두 “예외 없음”으로 실패했고, 수정 후
codec test 14개와 전체 solution 196개가 모두 통과했다. Codex adversarial

  `ReleaseVerifyRequest.RequireSignature`는 `SignatureVerifier` 없이 지정하면 거부하고,
  CLI는 07에서 서명 필수 option을 아예 제공하지 않는다. `signature.state`가 무엇을
  확인했고 무엇을 확인하지 않았는지 그대로 보고한다.
- `Math.Abs(long.MinValue)`가 던지는 `OverflowException`이 `Program`에서 잡히지 않아
  `schemaVersion: -9223372036854775808`짜리 설정이 exit 134와 stack trace로 죽었다.
  경계를 상·하한 비교로 바꾸고, 최상위에 마지막 `catch (Exception)`을 두어 모든 종료가
  문서화된 네 exit code 중 하나에 들어가게 했다.
- `ReadScalar`가 `Scalar.Tag`를 보지 않아 `!!str 1`이 정수 1이 됐다. 내장 tag를
  허용한다고 해놓고 무시하고 있었다. 명시적 tag가 철자·인용보다 우선하도록 고치고,
  허용 tag를 값 모델이 정의한 `!!str`·`!!int`·`!!bool`·`!!null`·`!!map`·`!!seq`로
  한정했다. `!!float`·`!!binary`는 내장 tag여도 canonical JSON이 표현할 수 없어 거부한다.

**Runtime manifest 읽기 상한 (08 단계 파일, 사용자 지시로 함께 처리):**

- `PackageRuntime.ReadManifestBytesAsync`가 transport stream을 상한 없는
  `MemoryStream`에 복사한 뒤에야 `manifestHash`를 검증했다. 고장났거나 악의적인
  endpoint가 첫 무결성 검사 전에 client 메모리를 고갈시킬 수 있다.
- 64 MiB 상한을 넘는 순간 더 읽지 않고 `runtime.manifest-invalid`로 중단한다. 재시도하지
  않는다. 이 manifest일 수 없는 크기의 응답은 일시적 실패가 아니라 고장난 endpoint이고,
  재시도는 상한을 두 번 더 소진할 뿐이다.
- artifact object는 이미 `RuntimeHashingWriteStream`이 manifest가 선언한 크기를 상한으로
  streaming 검증하므로 상한이 필요 없다. 상한이 없는 응답은 manifest 하나뿐이었다.

**자체 발견:** `BuiltInTag_IsAllowedWhileAnApplicationTagIsNot` 테스트가
`(string?)document["packageId"]`로 단언하고 있었다. 정수 token도 `(string?)` 캐스팅이
`"1"`을 주므로 값이 틀린 채로 통과했다. token type 단언으로 바꿨다.

**검증:** 전체 solution 376개 통과. 네 수정을 각각 임시로 되돌려 확인했다 —
`RequireSignature` 사전조건 1건, `Math.Abs` 경계 2건, tag 해석 5건, manifest 상한 2건만
실패하고 나머지는 통과했다. manifest 상한을 되돌리면 끝나지 않는 stream을 읽다
`MemoryStream`이 2GiB 한계에서 `IOException: Stream was too long`으로 죽는다. 실제 CLI
바이너리로 위조 서명·`long.MinValue`·`!!str` 재현 케이스가 모두 exit `1`과 JSON envelope로
바뀐 것도 확인했다.

### ✅ 수정/구현: 07 adversarial review 2회차 — Runtime 복구 전이

**배경:** manifest 읽기 상한을 넣은 뒤 다시 돌린 adversarial review에서 2건이 나왔다. 둘 다
`PackageRuntime`의 복구 전이이고, 07 CLI·Packager 코드에는 지적이 없었다. 08 단계 파일이지만
사용자 지시로 여기서 처리했다.

**수정:**

- `LoadStateAsync`가 현재 active manifest를 읽을 때 `ManifestInvalid`만 복구 대상으로 삼았다.
  과거 release의 manifest를 회수하면 `TransportFailed`가 그대로 빠져나가, 새 target과 artifact가
  멀쩡한데도 client가 갱신할 수 없고 로컬 state를 손으로 지워야만 풀렸다. `allowRecovery`일 때는
  이유를 가리지 않고 검증된 target에서 다시 만든다. 호출자가 이미 target을 검증했고 재사용하는
  installation은 전부 target 기준으로 다시 검증하므로 안전하다.
- `TransitionOptionalGroupAsync`가 재사용 실패 시 항상 `stale`을 유지했다. A→B로 stale이 된
  optional 데이터가 손상된 뒤 A로 rollback하면 `verifiedManifestHash`가 target과 같은 `stale`이
  되는데, `PackageStateValidator`는 이를 거부한다. 매 rollback이 `state-invalid`로 실패하고 빠져
  나갈 방법이 없었다. 마지막 검증 manifest가 곧 target이면 `notInstalled`로 전이한다.

**트레이드오프:** 첫 수정은 일시적 장애로 옛 manifest를 못 읽어도 state를 버린다. optional group을
다시 설치해야 하지만, "영구히 갱신 불가"보다는 낫다는 판단이다. 더 보수적인 대안(manifest 없이도
group 목록만 살리기)은 `StateSnapshot` 의미를 바꾸는 08 설계 변경이라 하지 않았다.

**검증:** 전체 solution 379개 통과. 두 수정을 함께 되돌리면 새 테스트 2건만 실패한다. 온전한
stale 데이터의 rollback이 여전히 다운로드 없이 `ready`로 재연결되는지도 함께 확인해, 새 guard가
정상 경로의 재사용을 뺏지 않는지 검증했다.

`docs/contracts/runtime.md`

### ✅ 수정/구현: 07 adversarial review 3회차 — 선언 크기 미강제 3건

**배경:** 2회차에서 Runtime manifest에만 상한을 넣었더니, 3회차 리뷰가 "같은 논리가 적용돼야
하는데 안 된 곳"을 전부 찾아왔다. 2회차에 내가 "manifest가 유일한 무제한 읽기"라고 판단한 건
Runtime 안에서만 맞았고 Packager는 보지 않았다.

**수정:**

- file artifact 압축 해제에 상한이 없었다. 저장 object는 크기·SHA-256이 고정이지만 **해제 결과
  크기는 고정이 아니다.** 작고 자기 일관적인 zstd object가 무한정 팽창할 수 있고, 크기 검사는
  해제가 끝난 뒤에 돌았다. `verify`에서는 CPU를, **`compact` 복원에서는 실제 파일에 직접 쓰므로
  디스크를** 소모한다(리뷰가 언급하지 않은 경로). `MaximumLengthWriteStream`을
  `BundleArchiveReader` 내부 중첩 클래스에서 공용 타입으로 올려 두 곳에 걸었다. bundle 해제는
  처음부터 이 상한을 쓰고 있었다.
- `ReleaseManifestReader.ReadPublishedBytesAsync`와 `manifest.sig` 읽기가 `File.ReadAllBytesAsync`로
  전체를 할당한 뒤에야 검증했다. `BoundedFile`로 manifest 64 MiB(Runtime과 동일), 서명 4 KiB
  상한을 걸었다. 길이를 먼저 보고, FIFO·문자 장치처럼 길이를 못 믿는 경우를 위해 읽는 중에도 센다.
- `StreamMatchesAsync`가 EOF까지 다 읽은 뒤 크기를 비교했다. 선언 크기까지만 읽고 한 byte를 더
  확인하는 방식으로 바꿨다. 모든 state 로드와 download plan이 지나는 경로다.

**설계 메모:** 사용자가 분할 압축으로 해결하는 안을 제시했으나 채택하지 않았다. 분할해도 chunk별
선언 크기를 강제하지 않으면 chunk 하나가 여전히 무한 팽창하고, 강제하는 순간 단일 frame에서도
똑같이 막힌다. 게다가 frame 경계 변경은 `artifactHash` 정의를 바꿔 golden vector를 무효화한다.
분할 압축은 임의 접근·병렬 해제 근거로 12단계 측정 뒤 판단할 사안이다(PRD 1033행).

**검증:** 전체 solution 386개 통과. 세 상한을 함께 되돌리면 Packager 2건이 실패하고 Runtime
cache 테스트는 **끝나지 않아 watchdog에 SIGKILL(exit 137)** 된다 — 상한이 없으면 끝없는 cache
stream을 영원히 읽는다는 뜻이다. 압축 폭탄 테스트는 codec이 실제로 만들어낸 byte 수를 세어
`선언 크기 + 청크` 이내에서 멈췄는지 확인한다. 정직한 codec과 선언 크기에 정확히 맞는 cache
항목이 여전히 통과하는지도 함께 확인해, 상한이 정상 경로를 깨지 않는지 검증했다.
