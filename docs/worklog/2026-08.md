### 파일 객체 경로에서 버전 폴더를 없애고 파일 이름에 버전 부착

- 작업: `files/<그룹 id>/<파일 버전>/<상대 경로>`를 `files/<그룹 id>/<상대 경로>@<파일 버전>`으로 바꿨다. 마이너 변경은 파일 몇 개만 건드리는데 버전 폴더 방식은 매번 파일 하나짜리 폴더 트리를 만든다.
- 작업: 버전을 원본 이름 뒤에 붙여 확장자를 쪼개지 않도록 규정했다. `.tar.gz`나 확장자 없는 파일도 같은 규칙으로 처리된다.

### 파일 객체 경로에 그룹 버전 폴더 복원

- 작업: 경로를 `files/<그룹 id>/<그룹 버전>/<상대 경로>@<파일 버전>`으로 확정했다. 폴더는 그룹 버전(메이저)까지만 나누고 리비전은 파일 이름에만 붙는다.
- 작업: 그룹 버전 폴더의 목적을 세대 단위 삭제로 문서에 명시했다. 그룹 버전을 올리면 새 세대가 새 폴더에 쌓이므로 이전 세대를 폴더째 지울 수 있다.

### 버전 구분자를 @에서 .v로 변경

- 작업: `@`가 안전한지 확인했다. Windows·macOS·Linux 파일 시스템과 .NET에서는 문제가 없고 RFC 3986도 path segment에서 `@`를 허용한다. 다만 AWS S3 객체 키 가이드가 `@`를 "특별 처리가 필요한 문자"로 지정하고 있다.
- 작업: 구분자를 `.v`로 바꿨다. `.`과 `v`만 쓰므로 RFC 3986 unreserved와 S3 safe 문자 집합에 모두 들어간다. `~`는 S3가 회피 대상으로 지정해 후보에서 제외했다.
- 작업: 규칙 2곳, 출력 레이아웃, 예시 경로 전체를 갱신하고 선택 근거를 PRD에 남겼다.

> 6. 권한 설정에 대한 설명을 추가해주고 그다음 내용은 리뷰가 하자는대로 만들어줘

#### 작업 결과

- 수행: upload PRD와 개발 계획의 지원 조건을 Supabase Pro 또는 Team으로 한정하고, 전역·버킷 파일 제한을 가장 큰 산출물보다 크게 설정해야 한다고 명시했다. TUS 청크 전송이 객체 크기 제한을 우회하지 않는다는 점도 함께 고정했다.
- 수행: 원격 `manifest.json` 조회와 원격 객체 검사를 제거했다. `<output>/.gpk-upload-state.json`에 마지막 업로드 성공 매니페스트를 원자적으로 기록하고, 이 상태가 없거나 손상되면 전량을 다시 올리도록 단순화했다.
- 수행: 산출물, `manifests/<releaseVersion>.json`, 루트 `manifest.json`을 모두 `UploadOrResume`과 `Upsert=true`로 게시하도록 정했다. 모든 원격 업로드가 끝난 뒤에만 로컬 성공 상태를 갱신하며, 실패하면 이전 상태를 보존한다.
- 수행: 직접 Storage API URL과 `apikey` 헤더 사용을 명시했다. 신뢰할 수 있는 로컬·CI에서는 RLS를 우회하는 secret key를 권장하고, 제한된 키는 대상 버킷의 `INSERT`·`SELECT`·`UPDATE` policy가 필요하다는 권한 설명을 추가했다.
- 수행: 원격 매니페스트 parser는 제거하고, 게시 순서와 단계별 실패 중단을 자동 검증할 수 있도록 단일 메서드 `IUploadStorage` 경계 하나만 개발 계획에 남겼다. 배포 PRD도 기술적 upsert와 세대 매니페스트의 논리적 불변성이 모순되지 않게 맞췄다.
- 검증: upload PRD 완료 조건 18개와 설계의 테스트 추적성 18개를 대조했고, 원격 조회 관련 문구가 제외 범위 외에 남지 않았음을 확인했다. `git diff --check`가 통과했다. 문서 변경만 수행해 빌드와 테스트는 실행하지 않았다.

### upload 리뷰 피드백과 게시 상태 보존 정책 반영

#### 사용자 입력

> 1. manifest.json .gpk-upload-state.json 추천대로 두파일만 깃에 저장하는 것으로 하자 백업은 이작업 범위 밖이니까 제외해줘
> 2. 방금 추천해준 방법으로 변경해줘
> 3. 모든 원격 경로를 업로드 전에 선검증하는 것만 작업해줘, 이름은 특수문자 같은 것들을 사용 못하게 할꺼니까 문제가 발생 할 것같은 이름이 있는지도 검증 하는 로직을 추가해주면 될 것같아
> 4. 제안한데로 제거해줘
> 5. 일단은 무시해줘
> 6. 동시 실행 금지를 명시해줘
> 7. 전환 대상 테스트를 추가해줘
>
> 리뷰에 대한 피드백이야 문서에 적용해줘

#### 작업 결과

- 수행: 별도 private 상태 Git 저장소가 마지막 게시 성공 시점의 `manifest.json`과 `.gpk-upload-state.json` 두 파일만 보존하도록 PRD와 release/upload 설계를 맞췄다. 실제 산출물의 Git·Git LFS 저장과 별도 object storage 백업은 제외하고, 깨끗한 실행 환경의 기존 Supabase 산출물 복원 자동화도 CLI 범위 밖으로 뒀다.
- 수행: 업로드 인증을 `GPK_SUPABASE_KEY=sb_secret_...` 전용으로 한정하고 `apikey` 헤더만 사용하도록 정했다. publishable·legacy `anon`·사용자 JWT와 RLS 대체 경로를 제거했다.
- 수행: 버킷 이름과 현재 매니페스트가 참조하는 모든 산출물 및 `manifests/<releaseVersion>.json`을 첫 Storage 호출 전에 ASCII 허용 문자 규칙으로 검사하도록 계획했다. 공백·비 ASCII·URL 예약문자·역슬래시·빈 세그먼트·`.`·`..`는 모두 보고하고 업로드하지 않으며, 기존 `gpk build` 경로 규칙은 바꾸지 않는다.
- 수행: 원격 루트 `manifest.json` 게시를 제거하고 소비자는 Postgres 포인터가 선택한 세대 매니페스트만 읽도록 정리했다. upload의 SHA-256 재검사는 추가하지 않고 기존 `gpk verify` 책임으로 유지했다.
- 수행: 같은 패치 데이터 프로젝트의 전체 파이프라인을 GitHub Actions concurrency 또는 운영 절차로 직렬화하고, 상태 Git push 전에 포인터나 다음 릴리스를 진행하지 않도록 명시했다. async 전환 대상인 `TestBuildCommand`, `TestVerifyCommand`, `TestCommandArguments`의 모든 `Program.Run` 호출부를 `Program.RunAsync`로 바꾸는 테스트 범위도 추가했다.
- 검증: upload PRD 완료 조건 22개와 설계 추적표 22행이 일치하고, 제거 대상인 원격 루트 매니페스트 게시·제한 권한 대안 문구가 남지 않았음을 확인했다. `git diff --check`가 통과했다. 문서 변경만 수행해 코드 빌드와 테스트는 실행하지 않았다.

### upload 재리뷰 6건과 불변 세대·SHA 재실행 계약 반영

#### 사용자 입력

> 1. 그렇게 해줘
> 2. 운영으로 관리할게
> 3. 논의 한대로 sha 기반으로 다시 빌드 가능하게 만들어줘
> 4. 그렇게 해줘
> 5. 버킷 문자 검증을 객체 경로 선검증 단계로 옮겨 한 번에 모아줘
> 6. 그렇게 해줘
>
> 리뷰에 대한 피드백이야 반영해줘

#### 작업 결과

- 수행: 세대 매니페스트를 산출물과 분리해 `Upsert=false`의 create-only 객체로 게시하도록 upload PRD·설계를 변경했다. 같은 세대 경로가 이미 있으면 원격 파일과 로컬 `manifest.json`의 바이트가 같을 때만 재사용하고, 다르면 기존 객체를 덮어쓰지 않고 버전 충돌로 중단한다. 이 결정은 이전 작업 일지의 세대 매니페스트 upsert 결정을 대체한다.
- 수행: 패치 데이터 배포는 GitHub Actions가 아니라 지정된 수동 배포 환경 한 곳에서 운영하도록 정했다. 첫 Storage 호출 뒤 실패하면 미리 기록한 `manifest.json.sourceCommit` SHA를 checkout해 같은 CLI·압축 구현 버전으로 `build` → `verify` → `upload`를 재실행하고, 완료 전에는 더 새로운 SHA를 게시하지 않는다. CLI `--commit`·`--rebuild` 옵션은 추가하지 않았다. CLI NuGet 배포용 GitHub Actions는 별도라 유지한다.
- 수행: 지정 배포 환경이 전체 Git 이력을 보유해 이전 성공 commit과 재실행 대상 SHA를 checkout할 수 있어야 한다고 명시했다. 상태 Git 저장소에는 기존 합의대로 `manifest.json`과 `.gpk-upload-state.json` 두 파일만 저장한다.
- 수행: Supabase resumable upload의 객체당 50 GB 상한을 로컬 선검증과 완료 조건·테스트 계획에 추가했다. 정확히 50 GB는 허용하고 초과 산출물은 첫 Storage 호출 전에 거부한다.
- 수행: 버킷 문자 검증을 `UploadSettingsResolver`에서 제거하고 `UploadCommand`의 객체 경로 선검증 단계로 옮겼다. 버킷, 모든 산출물 경로와 세대 매니페스트 경로의 오류를 한 번에 모아 보고하도록 생성자·테스트 계획을 맞췄다.
- 수행: `releaseVersion` 증가 조건을 “산출물이 달라지는 빌드”가 아니라 “`releaseVersion`을 제외한 매니페스트 내용이 이전 성공 매니페스트와 다른 빌드”로 CLI PRD·release 설계·배포 PRD에서 통일했다.
- 검증: upload PRD 완료 조건 22개와 upload 설계 추적표 22행을 대조했다. 패치 배포용 CI/concurrency, 세대 매니페스트 upsert, 버킷의 선행 단독 문자 검증과 무조건 원격 미조회 표현이 남지 않았음을 검색했고, Markdown 코드 fence·후행 공백과 `git diff --check`를 확인했다. 문서만 변경해 코드 빌드와 테스트는 실행하지 않았다.

### upload 재리뷰 피드백과 1 GiB 도구 상한 반영

#### 사용자 입력

> 1. 우리가 걱정할게 아닌거 같아. 추후에 문제가 발생하면 sdk 변경 같은 걸 할께 오류 로그를 잘 찍어줘
> 2. 그렇게 해줘
> 3. 일단 중요하게 명시해줘 다른 세션에서 작업할 거야
> 4. 일반 제약으로 툴 제약으로 1GB로 해줘 그이상 크기는 성능상 좋지 않을 것 같아

#### 작업 결과

- 수행: `Supabase.Storage` 내부 stream·file handle 수명은 SDK 책임으로 두고 별도 우회나 Windows handle 검증을 현재 범위에서 제거했다. 대신 Storage 실패 시 단계·원격 경로·예외 타입과 확인 가능한 HTTP 상태·Supabase 오류 코드·메시지를 출력하고 key·헤더·환경 변수 파일·전체 원시 응답 본문은 노출하지 않는 계약과 테스트를 추가했다.
- 수행: create-only 중복 판별을 HTTP 409의 `AlreadyExists`·`ResourceAlreadyExists`·`KeyAlreadyExists`와 legacy HTTP 400의 정확한 `Asset Already Exists`로 한정했다. 그 밖의 400·409는 원격 매니페스트를 다운로드하지 않고 실패하도록 PRD·설계·단위 테스트 계획을 맞췄다.
- 수행: 코드 관리 배포 스크립트가 상태 복원, 정확한 SHA 기록, CLI·압축 구현 버전 고정, 동시 실행 금지, 상태 push와 포인터 갱신을 책임하며 운영 배포의 필수 선행 조건임을 upload PRD·설계, distribution PRD와 releaseVersion 설계에 강조했다. 스크립트 구현은 별도 작업으로 남겼다.
- 수행: Supabase 서비스 한계와 별개로 `gpk upload` 산출물당 상한을 1 GiB(1,073,741,824바이트)로 낮추고 선검증·상수·경계 테스트·실제 업로드 범위를 변경했다.
- 검증: upload PRD 완료 조건 23개와 설계 추적표 23행이 일치하고, 이전 50 GB 경계·Windows handle 검증·22개 완료 조건 표현이 남지 않았음을 검색했다. Markdown code fence 수와 `git diff --check`를 확인했다. 문서 변경만 수행해 코드 빌드와 테스트는 실행하지 않았다.

### releaseVersion 기능(R1~R3) 구현

#### 사용자 입력

> GamePatchKit CLI에 releaseVersion 기능(R1~R3)을 구현한다.
>
> 기준 문서(반드시 전체를 Read):

> - docs/prd/gamepatch-kit-cli-prd.md 중 releaseVersion 관련 요구사항과 완료 조건
>
> 구현 대상: PatchManifest.cs에 ReleaseVersion 필수 필드 추가, ManifestStore.cs에 releaseVersion 검증·Sort 보존·HasSameReleaseContent 추가, BuildCommand.cs에 첫 값/유지/증가/int.MaxValue 중단 로직 추가. 기존 xUnit 통합 테스트 구조 안에서 TestManifestStore.cs·TestBuildCommand.cs에 테스트를 추가하고 docs/cli/build.md를 갱신한다.

#### 작업 결과

- 수행: `PatchManifest.ReleaseVersion`을 `schemaVersion` 뒤 `Order=1` 필수 필드로 추가하고 `SourcePath`·`SourceCommit`·`Groups`의 `Order`를 한 칸씩 미뤘다.
- 수행: `ManifestStore.Validate`에 `releaseVersion >= 0` 검증을 `schemaVersion` 검증 직후에 추가하고, `Sort`가 `ReleaseVersion`을 보존하도록 수정했다. `WriteAtomically`의 직렬화 절차를 `SerializeSorted`로 공통화하고, 양쪽 `ReleaseVersion`을 0으로 정규화한 뒤 같은 직렬화 설정으로 얻은 바이트를 비교하는 `HasSameReleaseContent(left, right)` 정적 메서드를 추가했다.
- 수행: `BuildCommand.Execute`가 그룹 빌드 완료 후 후보 매니페스트를 만들고 `ResolveReleaseVersion`으로 최종 값을 정하도록 했다. 이전 매니페스트가 없으면 0, `HasSameReleaseContent`면 이전 값 유지, 다르면 이전 값 + 1, 그 값이 필요한데 이전 값이 `int.MaxValue`면 `BuildException`으로 중단해 기존 `manifest.json`을 바꾸지 않는다.
- 수행: `TestManifestStore.cs`에 필수 필드 누락·음수 거부, `HasSameReleaseContent`의 releaseVersion만 다름·순서만 다름(true), sourcePath·sourceCommit·그룹 설정·아카이브·엔트리 차이(false) 테스트를 추가했다.
- 수행: `TestBuildCommand.cs`에 첫 빌드 0, 연속 변경 시 0→1→2, source 밖 커밋만 바뀌어도 증가, 무변경 재빌드 시 값·매니페스트 바이트 동일, int.MaxValue 초과 시 중단·매니페스트 보존 테스트를 추가했다.
- 수행: `docs/cli/build.md`에 releaseVersion 필드와 첫 값·유지·증가·상한 규칙을 설명하는 절을 추가했다.
- 검증: `dotnet build GamePatchKit.sln`이 0 경고·0 에러로 성공했고, `dotnet test GamePatchKit.sln`이 111개 전체(기존 99개 + 신규 12개) 통과했다. `codex-collab-workflow` standard review를 2회 진행(모델 gpt-5.6-terra)해 1차에서 테스트 커버리지 관련 Medium 1건(0이 아닌 이전 값에서의 증가, source 밖 커밋만 바뀐 경우 미검증)과 Low 1건(releaseVersion 필드 순서·round-trip 값 미검증)을 발견해 모두 테스트 보강으로 적용했고, 2차 재검토에서는 남은 finding이 없었다. git commit·push는 수행하지 않았다.

>
> 구현 대상: Directory.Packages.props에 Supabase.Storage 2.7.0 PackageVersion 추가하고 csproj에 PackageReference 추가(메타 패키지 Supabase는 참조하지 않음). #### 작업 결과

- 수행: `Directory.Packages.props`와 `GamePatchKit.Cli.csproj`에 `Supabase.Storage` 2.7.0만 추가했다. `dotnet list package --include-transitive`로 전이 의존성이 `BirdMessenger`·`MimeMapping`·`Supabase.Core`뿐이고 메타 패키지 `Supabase`나 Gotrue·Postgrest·Realtime·Functions가 없음을 확인했고, `dotnet pack` 결과물의 `tools/` 폴더 DLL 목록으로도 재확인했다.
- 수행: `Program.cs`의 `Main`을 `async Task<int>`로, `Run`을 `RunAsync`(`async Task<int>`)로 바꿨다. `build`·`verify` 분기는 기존 동기 `Execute` 호출을 그대로 유지했다(`Task.Run` 등으로 감싸지 않음). `upload` case는 이번 단계에서 추가하지 않았다. `net10.0`/`TreatWarningsAsErrors=true` 환경에서 await 없는 `async Task<int>`가 CS1998 경고 없이 빌드됨을 실측으로 확인했다.
- 수행: 신규 `UploadStorage.cs`에 `IUploadStorage`(`UpsertArtifactAsync`, `CreateOrVerifyManifestAsync`)와 `SupabaseUploadStorage`를 추가했다. 실제 API는 restore한 패키지를 리플렉션으로 직접 조사해 확인했다(`Client` 생성자, `IStorageFileApi<FileObject>`의 `UploadOrResume`/`Upload`/`Download` 오버로드, `SupabaseStorageException.Reason`/`StatusCode`/`Content`, `FailureHint.Reason` enum). 생성자는 `UploadSettings`만 저장하고 `Client`는 첫 게시 메서드 호출 시 지연 생성하며 `StorageUrl` 끝 `/`를 제거하고 `apikey` 헤더만 사용한다. `UpsertArtifactAsync`는 `UploadOrResume`·`Upsert=true`·`application/octet-stream`, `CreateOrVerifyManifestAsync`는 비-resumable `Upload`·`Upsert=false`·`application/json`을 쓰고, 중복 객체 오류일 때만 원격 바이트를 내려받아 로컬과 비교해 같으면 재사용·다르면 `BuildException`으로 중단한다. `IsDuplicateObjectError`는 HTTP 409의 `Reason.AlreadyExists` 또는 JSON `code`의 `ResourceAlreadyExists`/`KeyAlreadyExists`, legacy HTTP 400의 JSON `message` 정확 일치 또는 공백 제거한 원문 정확 일치만 참으로 판정한다. `FormatStorageFailure`는 stage·remotePath·exceptionType과 확인 가능한 statusCode·errorCode·errorMessage만 담고, `SupabaseStorageException.Content`를 JObject로 파싱해 `code`/`message` 필드만 추출해 원시 응답 본문·헤더·API key를 노출하지 않는다. `FileOptions` 타입 충돌은 `using FileOptions = Supabase.Storage.FileOptions;` alias로, `Download` 오버로드 모호성은 `transformOptions: null` named argument로 해결했다.
- 수행: 신규 `TestSupabaseUploadStorage.cs`에 `IsDuplicateObjectError`·`FormatStorageFailure` 순수 로직(네트워크 없음) 단위 테스트를 추가했다. `TestBuildCommand.cs`·`TestVerifyCommand.cs`·`TestCommandArguments.cs`의 `Program.Run` 호출부 4곳을 `await Program.RunAsync`로 바꾸고 감싸는 테스트 메서드를 `async Task`로 전환했다.
- 검증: `dotnet build`·`dotnet test`·`dotnet pack GamePatchKit.sln`이 모두 0 경고·0 에러로 성공했고 테스트 150개(직전 138개 + 신규 12개) 전체 통과했다. `codex-collab-workflow` standard review를 같은 스레드에서 2회 진행(모델 gpt-5.6-terra). 1차에서 Medium 1건(legacy HTTP 400 판정에서 JSON `message`에도 `Trim()`을 적용해 공백 포함 메시지를 잘못 중복으로 인정)을 발견해 `message == LegacyDuplicateMessage`로 수정하고 회귀 테스트를 추가해 적용했다. 2차 재검토에서 finding 해소를 확인했고 추가 finding은 없었다. git add·commit·push는 수행하지 않았다.

### releaseVersion + upload 전체 회귀·완결성 최종 점검

- 검증: 나열한 10개 문서 경로가 모두 실제로 존재하는지 확인했고, 후행 공백이 없는지 확인했다. 문서 전용 변경이라 별도 빌드·테스트는 수행하지 않았다. `git add`·`commit`·`push`는 수행하지 않았다.

### CLI standalone 실행파일을 GitHub Release에 포함

#### 사용자 입력

> cli 실행파일을 포함하고 싶은데

#### 작업 결과

- 수행: 기존 Windows x64, Linux x64, macOS Apple Silicon 테스트 매트릭스에서 `GamePatchKit.Cli`를 self-contained single-file로 publish하고 각 실행파일로 zstd build·verify smoke를 수행하도록 GitHub Actions를 확장했다. 실행 권한을 보존하는 플랫폼별 `tar.gz`를 workflow artifact로 전달하고, Release publish job이 NuGet 게시 후 `.nupkg`와 세 standalone 아카이브를 같은 GitHub Release에 첨부하도록 했다. Release asset 쓰기 권한은 publish job의 `contents: write`로만 제한했다.
- 수행: `README.md`와 `docs/cli/distribution.md`에 standalone 다운로드 방식과 자산 이름을 추가했다. 로컬 macOS 산출물은 ad-hoc 서명만 포함해 Gatekeeper 평가에서 거부되는 것을 확인했으며, 별도 Apple Developer ID 서명·공증 전에는 macOS에서 .NET tool 설치를 우선 사용하도록 제약을 명시했다.
- 검증: macOS ARM64 실행파일을 publish하고 원본과 `tar.gz` 재추출본으로 smoke를 각각 통과했으며, Linux x64 ELF와 Windows x64 PE single-file 및 아카이브 생성도 확인했다. Release 테스트 192개, actionlint 1.7.12와 `git diff --check`가 통과했다. `dotnet format --verify-no-changes`는 이번 변경과 무관하고 수정하지 않은 기존 C# 파일 6개의 EOF 개행 차이로 실패했다. 실제 Windows·Linux 실행과 GitHub Release asset 업로드는 workflow 실행 전이라 아직 확인하지 않았다.

#### 다음 작업

- 변경을 push한 뒤 GitHub Actions의 Windows·Linux·macOS matrix와 실제 Release asset 업로드를 확인한다.
- macOS standalone을 기본 설치 경로로 제공하려면 Apple Developer ID 서명·공증을 별도 작업으로 구성한다.

### main merge 후 CLI 자동 Release 생성

#### 사용자 입력

> main에 머지가 되면 release에 cli들을 만들어 주는 것으로 해줘

#### 작업 결과

- 수행: 수동 GitHub Release `published` 트리거를 제거하고 `main` push에서만 publish job이 실행되도록 변경했다. `Directory.Build.props`의 `<Version>`을 NuGet 버전과 `v<Version>` Release tag로 사용하며, 세 플랫폼 검증 후 NuGet 게시와 GitHub Release 생성·자산 첨부를 자동 수행한다.
- 수행: publish job을 `gamepatchkit-cli-release` concurrency group으로 직렬화하고, NuGet 게시 전에 같은 원격 tag가 있는지 `git ls-remote --exit-code`로 검사한다. 이미 게시된 버전이면 `<Version>` 증가를 요구하며 중단하고, 태그 조회 자체가 실패한 경우도 게시하지 않는다. Release 생성은 publish job의 `GITHUB_TOKEN`과 `contents: write`만 사용한다.
- 수행: `docs/cli/distribution.md`에 main merge·직접 push의 자동 게시, merge 전 버전 증가, NuGet만 성공한 실패 실행의 `--skip-duplicate` 재개 규칙을 반영했다.
- 검증: actionlint 1.7.12, Release 테스트 192개와 `git diff --check`가 통과했다. 원격 `main`이 존재하고 현재 `v0.1.0` tag는 없으며, 없는 tag 조회가 Bash에서 종료 코드 2가 되는 것을 확인했다. 실제 NuGet 게시와 GitHub Release 생성은 외부 상태를 바꾸므로 실행하지 않았다.

#### 다음 작업

- GitHub 저장소에 `NUGET_API_KEY`를 등록한 뒤 `<Version>`을 확인하고 변경을 `main`에 merge해 최초 자동 게시 결과를 확인한다.

### version tag를 NuGet 패키지 버전으로 우선 사용

#### 사용자 입력

> 그리고 tags에 v0.1.6 같이 버전이 들어오면 그것을 기준으로 nuget에 배포해줘

#### 작업 결과

- 수행: push trigger를 모든 branch와 `v*` tag로 명시하고, version tag push에서는 `Directory.Build.props` 대신 tag의 선행 `v`를 제거한 값을 NuGet 패키지·standalone 자산 버전으로 사용하도록 변경했다. `v0.1.6`은 패키지 버전 `0.1.6`과 Release tag `v0.1.6`으로 전달된다.
- 수행: publish job이 main push뿐 아니라 `refs/tags/v...`에서도 실행되도록 확장했다. main 경로는 새 tag를 생성하고, version tag 경로는 `gh release create --verify-tag`로 push된 기존 tag를 검증해 GitHub Release와 동일한 네 자산을 게시한다. `v`로 시작하지 않는 tag는 workflow push 대상에서 제외했다.
- 수행: `docs/cli/distribution.md`에 main의 `<Version>` 기준과 version tag 우선 기준, 두 경로의 tag 존재 검사 차이를 구분해 기록했다.
- 검증: actionlint 1.7.12, Release 테스트 192개와 `git diff --check`가 통과했다. Bash 버전 해석 검증에서 main은 `0.1.0`/`v0.1.0`, tag `v0.1.6`은 `0.1.6`/`v0.1.6`으로 확인했다. 실제 tag push, NuGet 게시와 GitHub Release 생성은 외부 상태를 바꾸므로 실행하지 않았다.

#### 다음 작업

- `NUGET_API_KEY` 등록 후 main merge 또는 `v<version>` tag push 중 선택한 최초 게시 경로를 실제 GitHub Actions에서 확인한다.
