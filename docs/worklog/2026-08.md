### 파일 객체 경로에서 버전 폴더를 없애고 파일 이름에 버전 부착

- 작업: `files/<그룹 id>/<파일 버전>/<상대 경로>`를 `files/<그룹 id>/<상대 경로>@<파일 버전>`으로 바꿨다. 마이너 변경은 파일 몇 개만 건드리는데 버전 폴더 방식은 매번 파일 하나짜리 폴더 트리를 만든다.
- 작업: 버전을 원본 이름 뒤에 붙여 확장자를 쪼개지 않도록 규정했다. `.tar.gz`나 확장자 없는 파일도 같은 규칙으로 처리된다.
- 작업: 규칙 서술 2곳, 출력 레이아웃, 예시 2·3·4·7의 경로를 모두 갱신했다.

### 파일 객체 경로에 그룹 버전 폴더 복원

- 작업: 경로를 `files/<그룹 id>/<그룹 버전>/<상대 경로>@<파일 버전>`으로 확정했다. 폴더는 그룹 버전(메이저)까지만 나누고 리비전은 파일 이름에만 붙는다.
- 작업: 그룹 버전 폴더의 목적을 세대 단위 삭제로 문서에 명시했다. 그룹 버전을 올리면 새 세대가 새 폴더에 쌓이므로 이전 세대를 폴더째 지울 수 있다.

### 버전 구분자를 @에서 .v로 변경

- 작업: `@`가 안전한지 확인했다. Windows·macOS·Linux 파일 시스템과 .NET에서는 문제가 없고 RFC 3986도 path segment에서 `@`를 허용한다. 다만 AWS S3 객체 키 가이드가 `@`를 "특별 처리가 필요한 문자"로 지정하고 있다.
- 작업: 구분자를 `.v`로 바꿨다. `.`과 `v`만 쓰므로 RFC 3986 unreserved와 S3 safe 문자 집합에 모두 들어간다. `~`는 S3가 회피 대상으로 지정해 후보에서 제외했다.
- 작업: 규칙 2곳, 출력 레이아웃, 예시 경로 전체를 갱신하고 선택 근거를 PRD에 남겼다.

### 승계 산출물 SHA-256을 `gpk verify` 명령으로 분리

#### 사용자 입력

> 7번(승계 산출물 SHA-256을 gpk verify 명령으로 분리부분도 작성해줘

#### 작업 결과

- 수행: 증분 빌드의 전제 2에서 SHA-256 재계산을 빼고 존재 여부·`storedSize`까지만 남겼다. 승계 산출물의 바이트는 빌드의 입력이 아니라 검사해도 매니페스트 내용이 달라지지 않는 반면 비용은 변경량이 아니라 승계 산출물 총량에 비례한다는 근거를 PRD와 설계에 적고, 전제 1·3과 전제 2의 성격이 다르다는 구분도 명시했다.
- 수행: `gpk verify --output <폴더>` 명령을 추가했다. 매니페스트가 참조하는 모든 아카이브·파일 객체를 존재 → 실제 크기 → SHA-256 순으로 검사하고, 첫 실패에서 멈추지 않고 전부 나열한 뒤 0이 아닌 종료 코드로 끝낸다. `--source`·Git 저장소·`gamepatchkit.yml`을 요구하지 않으며 미참조 객체 보고, 아카이브 해제 재확인, 손상 복구는 넣지 않았다.
- 수행: 저장된 파일에서 크기와 SHA-256을 얻는 `ArtifactWriter.ReadStored`를 단일 구현으로 두어 아카이브 재사용 판정과 `verify`가 같은 코드를 쓰게 했다. 2 GB 초과 아카이브를 위해 스트리밍 계산을 요건으로 못박았다.

- 수행: verify를 P8로 넣고 기존 P8·P9를 P9·P10으로 옮겼다. P6·P7의 "동일 크기 바이트 변조" 검증은 build 성공 + verify 검출로 바꿨다.
- 수행: `--output`을 매니페스트 참조 산출물을 모두 보관하는 완전한 저장소로 확정하고, 참조 산출물을 지우고 매니페스트만 남기는 스테이징 방식은 지원하지 않음을 설계 확정 사항에 적었다.
- 검증: PRD 완료 조건 22개와 설계 테스트 추적 항목 22개가 일치하고, P1~P10의 완료 조건 연결 합집합이 1~22를 모두 덮으며, `git diff --check`가 통과했다. 문서만 변경해 빌드·테스트는 실행하지 않았다.
