# GamePatchKit CLI Supabase 업로드

## 목적

`gpk build`가 만든 패치 데이터를 Supabase Storage 버킷에 올리는 `gpk upload` 명령을 추가한다.

업로드에 필요한 값은 CLI가 아니라 패치 데이터 프로젝트가 관리한다. 프로젝트마다 대상 버킷과 키가 다르고 키는 저장소에 커밋할 수 없으므로, 환경 변수로 받고 파일로도 넘길 수 있게 한다.

## 개발 환경

| 항목 | 버전 |
| --- | --- |
| Supabase.Storage | 2.7.0 |

- `Supabase.Storage`는 `netstandard2.0`으로 배포되어 `net10.0`에서 참조할 수 있다. 전이 의존성은 `BirdMessenger` 4.0.0, `MimeMapping` 4.0.0, `Newtonsoft.Json` 13.0.2, `Supabase.Core` 1.2.0, `System.Diagnostics.DiagnosticSource` 8.0.1이며 모두 `netstandard2.0` 이상이다.
- 메타 패키지 `Supabase`는 참조하지 않는다. Gotrue·Realtime·Postgrest·Functions까지 끌어오는데 이번 범위에서 쓰는 것은 Storage뿐이다.
- `Supabase.Storage`가 요구하는 `Newtonsoft.Json` 13.0.2는 CLI가 이미 고정한 버전과 같아 버전 충돌이 없다.
- `Supabase.Storage`의 업로드 API는 `Task`만 제공한다. `upload` 경로는 async로 만들고 `Program.Main`을 `async Task<int>`로 바꾼다. `build`와 `verify`의 동기 경로는 그대로 둔다.

## 요구사항

### 명령

```
gpk upload --output <패치 데이터 폴더> [--env-file <환경 변수 파일>]
```

- `--output`은 필수다.
- `--source`를 받지 않는다. 매니페스트가 올릴 대상을 모두 담고 있어 자기서술적이고, 업로드가 필요한 자리에는 소스 체크아웃이 없기 때문이다. `verify`와 같은 이유다.
- Git 저장소와 `gamepatchkit.yml`을 요구하지 않는다.

### 설정 값

| 이름 | 의미 |
| --- | --- |
| `GPK_SUPABASE_URL` | Supabase 프로젝트 URL |
| `GPK_SUPABASE_KEY` | 대상 버킷에 쓰기 권한이 있는 키 |
| `GPK_SUPABASE_BUCKET` | 업로드할 버킷 이름 |

- 세 값을 모두 요구한다. 하나라도 비어 있으면 빠진 이름을 모두 나열하고 아무것도 올리지 않은 채 중단한다.
- 프로세스 환경 변수를 먼저 읽고, `--env-file`을 지정했으면 그 파일의 값으로 덮어쓴다. 명령에 적은 것이 실제로 쓰이는 값이어야 하며, 로컬 셸이나 사용자 프로필에 남은 오래된 변수가 방금 지정한 파일을 조용히 이기는 상태를 만들지 않는다.
- `--env-file`의 경로가 없으면 중단한다. 지정했는데 읽히지 않은 것을 성공으로 넘기지 않는다.
- 환경 변수 파일은 줄마다 `KEY=VALUE` 하나를 적는다. 빈 줄과 `#`으로 시작하는 줄은 건너뛰고, 키와 값의 앞뒤 공백은 제거하며, 첫 `=`까지가 키다. 위 세 이름 외의 키는 무시한다.
- 키 값을 표준 출력·표준 에러 어디에도 출력하지 않는다. 실패 메시지에도 넣지 않는다.
- 환경 변수 파일은 키를 담으므로 패치 데이터 저장소에 커밋하지 않는다.

### 업로드 대상

1. `--output`의 `manifest.json`을 읽고 `gpk verify`와 같은 관계 검증을 수행한다. 위반이 있으면 아무것도 올리지 않고 중단한다.
2. 올릴 대상은 매니페스트가 참조하는 산출물이다. `archive`와 `source: file` 엔트리의 `name`을 올리고, `source: archive` 엔트리는 아카이브 안에 있으므로 따로 올리지 않는다.
3. 각 산출물의 로컬 존재 여부와 실제 크기 대 `storedSize`를 먼저 확인한다. 하나라도 없거나 크기가 다르면 아무것도 올리지 않고 중단한다.
4. SHA-256을 다시 계산하지 않는다. 전량 해시는 `gpk verify`가 담당하며, 배포 직전 검증이 필요하면 `gpk verify`를 먼저 실행한다.
5. 원격 경로는 `--output` 기준 상대 경로인 `name`을 그대로 쓴다. 매니페스트의 `name`이 이미 `/` 구분자의 상대 경로이므로 변환하지 않는다.

### 이미 올라간 산출물 판정

원격 `manifest.json`을 받아 그것이 참조하는 산출물 이름을 이미 올라간 것으로 본다. 로컬 매니페스트가 참조하는 산출물 중 이 목록에 없는 것만 올린다.

- 원격에 `manifest.json`이 없으면 첫 업로드로 보고 전부 올린다.
- 원격 매니페스트도 관계 검증을 통과해야 한다. 통과하지 못하면 이름 목록을 신뢰할 수 없으므로 중단한다.
- 객체를 하나씩 조회해 존재를 확인하지 않는다. 매니페스트를 마지막에 올리므로 원격 매니페스트가 있다는 것은 그것이 참조하는 산출물이 모두 올라갔다는 뜻이다. 로컬 빌드가 `manifest.json` 하나를 실패 복구의 기준점으로 삼는 것과 같은 성질을 원격에서도 쓴다.
- 업로드 도중 실패하면 원격 매니페스트는 이전 세대를 가리킨 채 남는다. 재실행은 같은 원격 매니페스트로 대상을 다시 계산하므로, 실패한 실행이 이미 올린 산출물은 다시 올라간다. 한 번의 중단분에 한정된 재전송이며 결과는 같다.

### 업로드 순서와 방식

1. 매니페스트가 참조하는 산출물을 먼저 모두 올린다.
2. `manifests/<releaseVersion>.json`을 올린다. 소비자가 세대를 골라 받는 불변 사본이며 덮어쓰지 않는다.
3. 마지막에 `manifest.json`을 올린다.
4. `Supabase.Storage`의 일반 `Upload`는 파일 전체를 한 요청으로 보내 50 MB gateway 제한을 넘을 수 있으므로, 모든 산출물은 `UploadOrResume`으로 올린다. `UploadOrResume`은 tus로 파일을 6 MiB씩 잘라 조각마다 `PATCH` 요청 하나를 보내므로, 산출물이 아무리 커도 요청 하나의 크기가 6 MiB를 넘지 않는다. 이 값은 `Supabase.Storage`가 고정한 값이라 CLI가 바꿀 수 없다.
5. `FileOptions.Upsert`를 켠다. 같은 원격 경로에는 같은 바이트만 올 수 있으므로 덮어쓰기가 결과를 바꾸지 않는다. 파일 버전으로 식별하고 `build`가 기존 산출물을 덮어쓰지 않기 때문이다. 실패한 실행이 이미 올린 객체를 다시 올릴 때 별도 경로가 필요 없어진다.
6. `manifest.json`은 매번 내용이 달라지는 유일한 객체이며 같은 규칙으로 덮어쓴다.
7. `FileOptions.ContentType`은 아카이브·파일 객체에 `application/octet-stream`, 두 매니페스트에 `application/json`을 준다. 라이브러리 기본값이 `text/plain;charset=UTF-8`이라 지정하지 않으면 모든 산출물이 텍스트로 표시된다.

원격에 매니페스트가 두 벌 올라가며 쓰임이 다르다. `manifests/<releaseVersion>.json`은 세대마다 하나씩 남는 불변 사본으로 소비자가 읽는다. 루트 `manifest.json`은 이 도구가 "무엇을 마지막으로 게시했는지" 기록하는 자리이며, 다음 실행의 델타 계산 기준이다. 둘의 내용은 같지만 수명이 다르다.

루트 `manifest.json`을 마지막에 올리는 이유는 로컬 빌드와 같다. 이것이 가리키는 산출물은 항상 먼저 올라가 있어야 하며, 중간에 실패하면 이전 세대를 가리킨 채 남아 다음 실행이 그 지점부터 델타를 다시 계산한다.

### 업로드 요약 출력

올린 산출물 수와 총 바이트, 건너뛴 산출물 수를 출력한다. 매니페스트는 산출물 집계와 분리해 표시한다. 모두 성공하면 종료 코드 0, 중단하면 0이 아닌 값으로 끝낸다.

게시한 `releaseVersion`을 출력한다. CI가 업로드 성공 후 버전 포인터에 쓸 값이며, 이 값 없이는 다음 단계를 자동화할 수 없다.

## 완료 조건

1. `gpk upload --output <폴더>`가 매니페스트 참조 산출물을 모두 올린 뒤 `manifests/<releaseVersion>.json`을 올리고, 마지막에 `manifest.json`을 올리고 종료 코드 0으로 끝난다.
2. 같은 명령을 다시 실행하면 산출물은 모두 건너뛰고 매니페스트만 다시 올라간다. 요약의 건너뛴 산출물 수가 참조 산출물 수와 같다.
3. 파일 하나를 고쳐 증분 빌드한 뒤 업로드하면 새로 생긴 파일 객체와 매니페스트만 올라가고 기존 아카이브는 건너뛴다.
4. 원격에 `manifest.json`이 없으면 참조 산출물을 모두 올린다.
5. 50 MB를 넘는 아카이브도 `UploadOrResume`을 사용해 gateway 제한 없이 올라간다.
6. `GPK_SUPABASE_URL`·`GPK_SUPABASE_KEY`·`GPK_SUPABASE_BUCKET` 중 하나라도 없으면 빠진 이름이 **모두** 나열되고 아무것도 올라가지 않은 채 0이 아닌 종료 코드로 끝난다.
7. 같은 이름이 프로세스 환경 변수와 `--env-file`에 모두 있으면 `--env-file`의 값이 쓰인다. `--env-file`을 주지 않으면 프로세스 환경 변수만 쓴다.
8. `--env-file`의 경로가 없으면 아무것도 올리지 않고 중단한다.
9. `GPK_SUPABASE_KEY`의 값이 성공·실패 어느 경우에도 표준 출력과 표준 에러에 나타나지 않는다.
10. 매니페스트가 참조하는 산출물이 로컬에 없거나 실제 크기가 `storedSize`와 다르면 아무것도 올리지 않고 중단한다.
11. 로컬이나 원격의 `manifest.json`이 관계 검증을 통과하지 못하면 아무것도 올리지 않고 중단한다.
12. `gpk upload`에 `--source`를 주면 거부하고, Git 저장소와 `gamepatchkit.yml` 없이 실행된다.
13. `Supabase` 메타 패키지 없이 `Supabase.Storage`만 참조한 상태로 `net10.0`에서 복원·빌드·테스트가 통과한다.
14. 서로 다른 `releaseVersion`으로 두 번 업로드하면 `manifests/` 아래에 두 세대가 모두 남고, 이전 세대의 내용이 바뀌지 않는다.
15. 게시한 `releaseVersion`이 표준 출력에 나타나 CI가 버전 포인터에 쓸 값을 읽을 수 있다.

## 제외 범위

이번 범위를 업로드 한 방향으로 한정한다. 다음은 넣지 않는다.

- 다운로드, 삭제, 버킷 생성·설정
- **버전 포인터 갱신** — `gpk upload`는 Postgres를 건드리지 않는다. 게시한 `releaseVersion`을 출력하는 데까지가 이 명령의 범위이고, 포인터 갱신은 업로드가 성공한 뒤 CI가 한다. CLI에 DB 의존성을 넣지 않고도 "포인터가 마지막"이라는 순서가 지켜진다. 포인터의 역할은 [gamepatch-kit-distribution-prd.md](gamepatch-kit-distribution-prd.md)에서 다룬다
- 원격에 남은 미참조 과거 세대 정리와 보존 정책
- 캐시 정책 — `FileOptions.CacheControl`을 지정하지 않고 라이브러리 기본값(3600초)을 그대로 쓴다. `manifest.json`의 캐시 수명은 버킷·CDN 설정에서 정한다
- 서명 URL, 공개·비공개 전환, CDN 캐시 무효화
- 업로드 재시도와 백오프 — CLI가 별도 재시도를 걸지 않는다. `UploadOrResume`의 이어받기는 업로드 세션 URL을 프로세스 메모리(`UploadMemoryCache`)에만 두므로 `gpk upload`를 다시 실행하면 동작하지 않는다. 이 명령을 쓰는 이유는 이어받기가 아니라 청크 전송으로 단일 요청 크기 제한을 넘기지 않는 것이며, 중단 후 재실행은 원격 매니페스트 기준으로 대상을 다시 계산한다
- 병렬 업로드 — 객체를 하나씩 순서대로 올린다
- 원격 산출물의 무결성 확인 — 건너뛸 때 원격 바이트를 받아 검사하지 않는다
- 버킷이 다른 패치 데이터 프로젝트의 산출물을 담고 있는 경우 — 원격 매니페스트의 `sourcePath`가 로컬과 같은지 확인하지 않는다. 한 버킷은 한 패치 데이터 프로젝트가 쓴다고 본다
- `gpk build` 완료 후 자동 업로드 — `upload`는 독립 명령이다
- Supabase 외 스토리지 백엔드
