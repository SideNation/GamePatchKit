# GamePatchKit — 게임 데이터 패치 패키징·배포·적용 툴킷

## 개요

`GamePatchKit`은 게임 데이터(코드가 아닌 에셋·설정·테이블)를 폴더 단위로 패키징하고, 콘텐츠 주소 기반으로 CDN에 배포하고, 클라이언트가 변경분만 내려받아 안전하게 적용하게 하는 도구 모음이다. CLI(빌드·배포)와 런타임 라이브러리(다운로드·검증·적용)로 구성되며, 런타임은 Unity IL2CPP에서 동작하는 것을 전제로 한다.

기존 패처(Steam depot, Unreal BuildPatchServices, Riot 신규 패처, Unity Addressables)와 보안 프레임워크(TUF)를 조사해, 사용자가 요구한 기능 외에 **반드시 함께 만들어야 동작하는 항목**을 v1 범위에 포함했다. 조사 근거는 [리서치 근거와 반영 결정](#리서치-근거와-반영-결정)에 정리한다.

## 개발 v1

### 트리거

CLI 진입점 (개발자·CI가 호출):

| 명령 | 목적 |
| --- | --- |
| `gpk init` | 워크스페이스 루트에 `gamepatchkit.yml` 생성 |
| `gpk build` | 변경분만 패키징해 로컬 아티팩트·매니페스트 생성 (기본: git 증분) |
| `gpk repack` | 캐시·git 증분을 무시하고 전체 재패키징 |
| `gpk publish` | 아티팩트·매니페스트를 스토리지에 업로드 (불변 객체 우선, 채널 포인터 마지막) |
| `gpk promote` | 채널 포인터를 특정 릴리스로 이동 (롤아웃 비율·킬 스위치 포함) |
| `gpk verify` | 로컬 아티팩트 또는 원격 릴리스의 해시·서명 정합성 검사 |
| `gpk diff` | 두 릴리스 간 다운로드 크기·변경 파일 목록 산출 |
| `gpk gc` | 보존 정책 밖의 미참조 객체 정리 (mark → grace → delete) |
| `gpk key` | 서명 키 생성·회전·키셋 서명 |

런타임 진입점 (게임 클라이언트가 호출):

- 채널 확인 → 업데이트 필요 여부 판정
- 다운로드 계획 산출 (바이트 수·파일 수·필요 디스크)
- 다운로드·검증·적용 (일시정지·재개·취소 지원)
- 선택 패키지 온디맨드 설치
- 설치본 검사·복구
- 이전 버전으로 롤백

### 범위

**포함한다.**

1. CLI: 폴더 단위 yaml 설정, 압축/무압축 선택, Zstandard 기본 압축, 매니페스트 JSON 생성, git 기반 증분 패키징, 전체 재패키징
2. 콘텐츠 주소 객체 저장소와 CDN 레이아웃, 캐시 정책
3. 소파일 묶음(pack)과 HTTP range 부분 다운로드
4. Zstandard 사전(dictionary) 학습·배포
5. 런타임 라이브러리: 병렬·재개 가능 다운로드, 무결성 검증, 원자적 적용, 저널 기반 크래시 복구, 롤백
6. 무결성·서명 체계: 객체 해시, 매니페스트 서명, 키 회전, 다운그레이드·동결 공격 방어
7. 채널·단계적 롤아웃·킬 스위치
8. 보존 정책과 GC
9. Unity 패키지(asmdef·link.xml)와 IL2CPP 대응 규칙
10. CLI ↔ 런타임 상호 적합성(conformance) 테스트와 골든 벡터

**포함하지 않는다.**

- 실행 코드(어셈블리·네이티브 바이너리·스크립트) 배포 — 스토어 정책상 금지 영역이므로 데이터만 다룬다
- 자체 CDN·오리진 서버 구축 (정적 HTTPS 스토리지에 얹는 것을 전제)
- P2P 배포, 대역폭 셰이핑 인프라
- 에셋 빌드 파이프라인(텍스처 압축·AssetBundle 빌드 등) 자체
- 콘텐츠 제작 툴, 웹 대시보드

**아티팩트 형식**

```
<storage-root>/
  channels/<channel>.json           # 가변 포인터, 짧은 TTL, 서명됨
  keys/root.json                    # 루트 키셋, 서명됨
  manifests/<manifestHash>.json     # 불변, 긴 TTL
  objects/<h0h1>/<hash>             # 불변, 긴 TTL (압축 여부는 메타에 기록)
  packs/<h0h1>/<packHash>           # 불변, 소파일 묶음
  dicts/<dictHash>.zdict            # 불변, Zstandard 사전
```

**로컬 산출물**

```
<workspace>/
  gamepatchkit.yml                  # 루트 설정
  <folder>/package.yml              # 폴더별 패키지 설정
  .gamepatchkit/
    cache/                          # 빌드 캐시 (해시·압축 결과)
    build/                          # 업로드 대기 아티팩트
    state.json                      # 마지막 빌드 커밋·정책 지문
```

**클라이언트 설치 산출물**

```
<installRoot>/
  content/                          # 적용된 실제 파일 트리
  .gpk/
    installed.json                  # 현재 버전·패키지별 설치 상태
    journal.log                     # 적용 중 단계 저널 (크래시 복구용)
    objects/                        # 롤백용 이전 버전 객체 (보존 정책 내)
    staging/                        # 다운로드·해제 임시 영역
```

### 동작 규칙

#### 1. 개념 모델

1. **Workspace** — 게임 데이터가 들어 있는 git 저장소. 루트에 `gamepatchkit.yml`이 있다.
2. **Package** — 폴더 단위 패치 단위. 폴더에 `package.yml`을 두어 정의한다. 압축 정책·필수/선택·플랫폼·로케일 태그의 적용 단위다.
3. **Entry** — 패키지 안의 파일 하나. 논리 경로와 객체 참조를 갖는다.
4. **Object** — 콘텐츠 주소 blob. **키는 압축 전 원본 내용의 해시**다.
5. **Pack** — 소형 객체를 묶은 불변 컨테이너. 객체는 pack 안에서도 **개별 압축**된다.
6. **Manifest** — 릴리스 하나의 전체 목록. 자신도 해시로 주소화되고 서명된다.
7. **Release** — 매니페스트 + 버전 메타. 불변이다.
8. **Channel** — 릴리스를 가리키는 가변 포인터(`live`/`beta`/`qa`). 유일한 가변 자원이다.

객체 키를 압축 전 해시로 잡는 이유: 코덱 버전·압축 레벨이 바뀌어도 객체 정체성이 흔들리지 않아 불필요한 재업로드와 캐시 무효화가 생기지 않는다. 전송 검증용으로 압축 표현의 해시를 별도 필드에 함께 기록한다.

#### 2. 설정 (yaml, CLI 전용)

yaml은 CLI 빌드 입력에서만 쓰고, 배포물·런타임에는 절대 포함하지 않는다. 런타임이 읽는 것은 JSON뿐이다.

`gamepatchkit.yml` (루트)에 정의할 것:

- 프로젝트 ID, 스토리지 base URL, 채널 목록
- 기본 압축 정책(알고리즘·레벨·`auto` 판정 임계값), 해시 알고리즘
- pack 임계 크기·목표 크기, 사전 학습 on/off
- 전역 include/exclude 글롭
- 서명 키 참조, 보존 정책(채널별 유지 릴리스 수)

`package.yml` (폴더별)에 정의할 것:

- 패키지 ID·표시 이름
- include/exclude 글롭
- **압축 모드: `auto` | `zstd` | `none`** — 사용자가 요구한 "압축할지 파일 그대로 전송할지" 선택
- zstd 레벨, 사전 사용 여부
- 설치 종류: `required`(초기 필수) | `optional`(온디맨드)
- 플랫폼·로케일 태그, 다운로드 우선순위

`auto` 판정 규칙: 확장자가 이미 압축된 포맷(png·jpg·webp·ogg·mp4·zip·zst 등)이면 무압축, 아니면 압축 후 이득이 임계값(기본 5%) 미만이면 무압축으로 되돌린다. 판정 결과는 매니페스트에 명시적으로 기록해 런타임이 추측하지 않게 한다.

#### 3. 패키징 파이프라인 (`gpk build`)

1. 설정 로드 → **정책 지문(policy fingerprint)** 계산 (압축 정책·해시 알고리즘·pack 파라미터·사전 버전·글롭 포함)
2. 대상 파일 열거 — git이 추적하는 파일만 대상으로 한다. 미추적·ignore 파일은 기본 제외하고, 포함하려면 설정에 명시해야 한다
3. 증분 판정 (아래 4항)
4. 대상 파일 해시 → 객체 키 산출
5. 압축 정책 적용 → 압축 또는 원본 유지
6. 소형 객체를 pack으로 묶기 (패키지·경로 지역성 기준으로 묶어 한 패치가 건드리는 pack 수를 최소화)
7. 매니페스트 생성 → 정규 JSON 직렬화 → 매니페스트 해시 산출
8. 매니페스트 서명
9. 빌드 리포트 출력 (파일 수, 원본/전송 바이트, 압축률, 신규 객체 수, 소요 시간)

파이프라인은 파일 단위로 병렬 처리하며, 해시·압축·pack 적재가 겹쳐 돌아가게 한다.

#### 4. git 기반 증분 (사용자 요구: "깃으로 데이터 추적, 변경사항만 패치 데이터로")

- 릴리스 매니페스트에 `sourceCommit`을 기록한다.
- 다음 빌드는 `마지막 빌드 커밋 → HEAD` 변경 경로만 재해시·재압축하고, 나머지는 빌드 캐시의 객체 메타를 재사용한다.
- **증분을 포기하고 전체 스캔으로 폴백하는 조건** (하나라도 해당하면):
  1. 워킹 트리가 더티하다
  2. 마지막 빌드 커밋을 찾을 수 없다 (rebase·force push·shallow clone)
  3. 정책 지문이 바뀌었다
  4. 빌드 캐시가 없거나 손상됐다
- git은 **빌드 속도 최적화 수단일 뿐**이고, 클라이언트가 무엇을 받을지는 항상 **매니페스트 간 객체 집합 차이**가 결정한다. git 증분이 틀려도 결과 매니페스트가 옳으면 배포는 옳다. 이 불변식을 테스트로 고정한다(증분 빌드 결과 == 전체 빌드 결과).
- 파일이 이동·이름만 바뀌면 내용 해시가 같으므로 새 객체가 생기지 않는다.

#### 5. 전체 재패키징 (`gpk repack`)

- 빌드 캐시와 git 증분을 모두 무시하고 전 파일을 재해시·재압축한다.
- 코덱 버전·압축 레벨·사전을 교체할 때, 캐시 손상이 의심될 때, 결정성 검증이 필요할 때 사용한다.
- 객체 키가 원본 해시이므로, 재압축해도 내용이 같은 객체는 **재업로드 대상이 아니다**. 압축 표현이 바뀐 객체만 다시 올린다.
- `--verify-deterministic` 옵션으로 재빌드 결과 매니페스트 해시가 이전과 같은지 검사한다.

#### 6. 매니페스트 (JSON)

정규 직렬화 규칙: 키 오름차순 정렬, UTF-8 no BOM, LF, 공백 없음, 불변 문화권 숫자 포맷, `null` 필드 생략. 이 규칙 위에서 해시를 계산해야 재현 가능하다.

주요 필드:

| 영역 | 필드 |
| --- | --- |
| 릴리스 | `schemaVersion`, `projectId`, `version`, `versionSequence`(단조 증가 정수), `createdAt`, `sourceCommit` |
| 코덱 | `codec`, `codecVersion`, `codecParams`, `hashAlgorithm` |
| 패키지 | `id`, `install`(required/optional), `platforms`, `locales`, `priority`, `dictId`, `totalSize`, `entries` |
| 엔트리 | `path`, `objectId`(원본 해시), `size`, `storage`(`object`/`pack`), `compression`(`none`/`zstd`), `transferSize`, `transferHash`, `packId`, `packOffset`, `packLength`, `executable`/`attributes` |
| 참조 | `packs[]`(`packId`, `size`, `hash`), `dicts[]`(`dictId`, `size`, `hash`) |

경로 규칙: 항상 `/` 구분자, 상대 경로, `..`·절대 경로·드라이브 문자·심볼릭 링크 금지. 런타임은 적용 전 경로 정규화 후 설치 루트 밖으로 나가는 경로를 거부한다(경로 탈출 방어).

#### 7. 채널 포인터와 CDN 캐시 정책

`channels/<channel>.json`이 담을 것: `projectId`, `channel`, `version`, `versionSequence`, `manifestHash`, `manifestUrl`, `expiresAt`, `rollout`(`percentage`, `salt`), `minClientVersion`, `signature`.

캐시 정책:

- `objects/`, `packs/`, `manifests/`, `dicts/` → `Cache-Control: public, max-age=31536000, immutable`
- `channels/*.json`, `keys/root.json` → `max-age=30, must-revalidate` (짧은 TTL)

업로드 순서는 **불변 자원 전부 → 검증 → 채널 포인터 마지막**이다. 순서를 뒤집으면 클라이언트가 아직 없는 객체를 요청하는 창이 생긴다. `gpk publish`는 이 순서를 강제하고, 포인터 갱신 직전에 참조 객체 존재 여부를 확인한다.

#### 8. 클라이언트 적용 흐름

1. 채널 포인터 조회 → 서명 검증 → `expiresAt` 확인 → `versionSequence`가 현재 설치본 이상인지 확인
2. `manifestHash`로 매니페스트 조회 → 내용 해시 대조
3. 설치 상태와 대조해 **필요 객체 집합** 산출 (플랫폼·로케일·선택 패키지 필터 적용)
4. 다운로드 계획 산출 → 필요 여유 디스크 검사(스테이징 + 최종 반영 여유분) → 부족하면 시작 전에 실패
5. 다운로드
   - 기본 동시 연결 4~8개 (설정 가능)
   - pack은 필요한 구간만 HTTP range로 요청, 다중 range 지원 시 요청 수를 합침
   - range 미지원 서버면 객체 단독 URL로 폴백
   - 중단 지점부터 재개, 지수 백오프 재시도, **네트워크 오류는 기본적으로 치명적으로 취급하지 않는다**
   - 대역폭 상한·동시성은 런타임 옵션으로 조절 가능
6. 각 객체를 해제 후 원본 해시로 검증 → 불일치하면 해당 객체만 재다운로드
7. 스테이징 영역에 배치 → 저널에 단계 기록 → 원자적 반영(rename) → 저널 커밋
8. 설치 상태 갱신 → 이전 버전 객체는 보존 정책 내에서 남겨 롤백 가능하게 유지

크래시·강제 종료 후 재시작하면 저널을 읽어 미완 단계부터 이어간다. 적용 도중 취소해도 설치본은 "이전 버전 완전" 또는 "새 버전 완전" 중 하나여야 하며, 중간 상태로 게임이 뜨지 않는다.

**검사·복구**: 설치본 전체 또는 패키지 단위로 해시를 재검사해 누락·손상 파일을 찾아 다시 받는다.

**롤백**: 보존된 이전 릴리스 매니페스트로 되돌린다. 필요한 객체가 로컬에 없으면 CDN에서 다시 받는다(불변 객체이므로 항상 가능).

#### 9. 무결성·서명

- 객체마다 원본 해시와 전송 해시를 매니페스트에 기록한다. 해시 알고리즘은 SHA-256을 기본으로 한다(플랫폼 내장·하드웨어 가속, 네이티브 의존 없음).
- 매니페스트와 채널 포인터는 서명한다. 클라이언트는 빌드 시점에 **루트 공개키를 앱에 고정(pin)** 한다.
- **키 회전**: `keys/root.json`이 키셋과 임계 서명 수(threshold)를 담고, 새 키셋은 이전 키로 서명한다. 키 하나가 유출돼도 임계값 이상 확보 없이는 릴리스를 위조할 수 없다.
- **다운그레이드 공격 방어**: `versionSequence`가 설치본보다 낮은 포인터를 거부한다. 의도적 다운그레이드는 명시적 롤백 API로만 허용한다.
- **동결(freeze) 공격 방어**: 채널 포인터에 `expiresAt`을 두고, 만료된 포인터는 거부한다.
- 서명 알고리즘은 Unity IL2CPP에서 **순수 관리 코드로 검증 가능한 것**으로 고른다. 후보: Ed25519 순수 관리 구현, ECDSA P-256, RSA-2048/SHA-256. 최종 선택은 [결정이 필요한 항목](#결정이-필요한-항목) 참고.
- 개인키는 저장소에 두지 않는다. CI 시크릿 또는 KMS에서 주입한다.

#### 10. 채널·단계적 롤아웃

- 릴리스는 불변, 채널만 가변이다. 배포·롤백 모두 포인터 이동 한 번이다.
- 롤아웃 비율: 포인터의 `rollout.percentage`와 `rollout.salt`를 클라이언트 안정 식별자와 함께 해싱해 대상 여부를 판정한다. 같은 기기는 같은 판정을 유지한다.
- 킬 스위치: 비율을 0으로 내리거나 포인터를 이전 릴리스로 되돌린다. 이전 릴리스의 객체는 보존 정책상 남아 있으므로 즉시 복귀된다.
- `minClientVersion`으로 구버전 클라이언트가 호환되지 않는 릴리스를 받지 않게 막는다.
- QA는 특정 버전 고정(pin)으로 롤아웃 판정을 우회할 수 있다.

#### 11. 보존과 GC

- 채널별 최근 N개 릴리스와 명시적으로 고정한 릴리스의 매니페스트를 보존한다.
- 보존된 매니페스트가 참조하는 객체·pack·사전은 삭제 금지다.
- `gpk gc`는 mark(도달 가능 집합 계산) → grace(유예 기간, 기본 7일) → delete의 3단계로 동작한다. 유예 기간은 다운로드 중이던 클라이언트가 객체를 놓치지 않게 한다.
- 기본은 dry-run이며 실제 삭제는 명시 플래그가 필요하다.

#### 12. 결정성·재현성

- 정규 JSON 직렬화로 매니페스트 바이트를 결정적으로 만든다.
- 압축 결과 바이트는 라이브러리 버전에 따라 달라질 수 있다고 **가정한다**. 그래서 객체 정체성은 원본 해시로만 잡고, `codecVersion`·`codecParams`를 매니페스트에 기록한다.
- 같은 커밋·같은 설정으로 두 번 빌드하면 같은 매니페스트 해시가 나와야 한다. CI가 이를 검사한다.

#### 13. 관측성

- 로깅은 ZLogger로 통일한다. CLI는 구조화 로그 + 사람이 읽는 요약, 런타임은 호스트가 싱크를 주입할 수 있게 한다.
- 빌드 리포트: 파일 수, 원본/전송 바이트, 압축률, 신규 객체 수, 단계별 소요 시간.
- 런타임 진행 이벤트: 단계(확인/다운로드/검증/적용), 바이트 진행률, 현재 속도, 남은 시간 추정, 재시도 횟수.
- 실패 이벤트: 실패 단계, 객체 ID, HTTP 상태, 재시도 횟수 — 호스트가 텔레메트리로 보낼 수 있게 노출한다.

#### 14. AOT / IL2CPP 규칙

- Newtonsoft.Json 13.0.2 고정. 모든 매니페스트 모델은 명시적 `[JsonProperty]`를 붙이고, `TypeNameHandling`은 사용하지 않는다(AOT 위험이자 역직렬화 보안 위험).
- 런타임 코드 생성 금지: `System.Reflection.Emit`, 표현식 트리 컴파일, `dynamic`, 문자열 기반 `Type.GetType` 사용 금지.
- 런타임에서 만들어지는 제네릭 인스턴스화를 피하고, 매니페스트 모델은 구체 타입 컬렉션으로 고정한다.
- Unity 패키지에 `link.xml`을 포함해 매니페스트 모델과 컨버터를 보존 대상으로 지정한다.
- CI에 **IL2CPP 빌드 잡을 상시 포함**한다. 릴리스 직전에만 확인하면 늦다.
- 코덱은 `ICodec` 인터페이스 뒤로 숨긴다. 네이티브 코덱을 쓸 수 없는 플랫폼에서는 `none`(무압축) 경로만으로 동작이 성립해야 한다.

#### 15. 상호 적합성(conformance)

- CLI가 만든 아티팩트를 런타임이 100% 재현 적용할 수 있어야 한다.
- 골든 벡터를 저장소에 고정한다: 소형 데이터 세트 → 기대 매니페스트 JSON, 기대 객체 키 목록, 기대 pack 배치.
- 테스트 케이스: 빈 패키지, 파일 1개, 대용량 파일, 소파일 수만 개, 유니코드·긴 경로, 파일 삭제, 이름 변경, 내용만 변경, 압축 모드 3종, 선택 패키지 온디맨드, 다운로드 중단·재개, 적용 중 강제 종료 후 재개, 손상 객체 복구, 롤백.

**리스크**

1. **NativeCompressions 플랫폼 커버리지** — 조사 시점 기준 프리뷰에서 iOS IL2CPP 미지원, 일부 RID(win-arm64, linux-arm64, android-arm, android-x64, ios-x64) 미지원으로 안내되어 있다. Android·iOS가 주요 타깃이면 치명적이므로, **착수 전에 최신 상태를 직접 검증**해야 한다. 완화책: `ICodec` 추상화 + `none` 폴백 + 플랫폼별 코덱 가용성 매트릭스 테스트.
2. **Zstandard 사전 API 노출 여부** — 공개 문서에서 LZ4 사전 타입은 확인되나 Zstandard 사전 API는 명시되어 있지 않다. 미지원이면 사전 기능(9~10항의 압축률 이득)을 v1에서 빼거나 별도 바인딩이 필요하다. 착수 전 확인 항목이다.
3. **서명 알고리즘의 Unity 가용성** — BCL 내장 여부가 플랫폼마다 다르므로 순수 관리 구현으로 검증 가능한 조합을 실기기에서 먼저 확인한다.
4. **스토어 정책** — Apple 2.5.2, Google Play 모두 "실행 코드 다운로드 금지, 비실행 에셋은 허용" 기조다. 따라서 이 툴킷은 데이터만 다루고, 스크립트·어셈블리·네이티브 라이브러리를 패치 대상에 넣는 경로를 만들지 않는다.
5. **git 의존** — shallow clone·force push 환경에서 증분이 깨질 수 있다. 폴백 규칙(4항)으로 정확성은 보장하되 빌드 시간이 튈 수 있음을 감수한다.

### 리서치 근거와 반영 결정

사용자 요구 사항 외에 **함께 만들지 않으면 실제로 배포가 안 되는 항목**을 조사로 도출했다.

| 조사에서 확인한 것 | 반영 결정 |
| --- | --- |
| Riot은 버전 쌍 바이너리 델타(RADS)를 버리고 콘텐츠 정의 청킹 + 콘텐츠 주소 방식으로 전환했다. 델타 체인은 과거 8버전만 지원돼 오래된 클라이언트가 전체 재다운로드를 해야 했고, 패치 생성에 수 시간이 걸렸다 | v1을 **파일 단위 콘텐츠 주소 방식**으로 잡는다. 버전 쌍 델타를 만들지 않으므로 어느 버전에서 올라와도 "없는 객체만" 받으면 되고, 생성 비용이 릴리스 수에 비례하지 않는다 |
| Riot은 30만 개 청크를 5천 개 미만 번들로 묶어 HTTP 요청 수를 줄이고, 청크는 개별 압축해 부분 다운로드가 가능하게 했다. UE ChunkDownloader도 "소파일이 매우 많은 게임"을 대상으로 한다 | **pack + 개별 압축 + HTTP range**를 v1에 포함한다. 게임 데이터는 소파일이 많아 요청 수가 지배적 비용이 된다 |

| 매니페스트 캐시 정책 정석은 "불변 콘텐츠 주소 blob은 긴 TTL, 버전 포인터는 짧은 TTL, 매니페스트 URL은 해시로 버저닝" | CDN 레이아웃과 `Cache-Control` 규칙을 PRD에 명시했다 (7항) |

| TUF는 임계 서명·역할 분리·키 회전으로 키 유출 이후에도 방어하고, 롤백(다운그레이드) 공격과 동결 공격을 명시적으로 막는다 | `versionSequence` 단조성 검사, 포인터 `expiresAt`, 키셋 회전을 v1 보안 요구사항으로 넣었다 (9항) |
| Unity Addressables는 원격 카탈로그 해시 파일로 갱신을 감지하고, 이전 릴리스의 상태 파일을 보관해야 콘텐츠 전용 업데이트가 가능하다 | 채널 포인터 + 매니페스트 해시 구조로 같은 효과를 내고, 릴리스 매니페스트 보존을 GC 정책에 못 박았다 (11항) |

| bsdiff/xdelta/zstd `--patch-from`은 실행 파일처럼 "조금만 바뀌는 큰 바이너리"에서 강하지만, 버전 쌍마다 패치를 만들어야 하고 생성 비용이 크다 | v1에서 제외하고 v2 후보로 남긴다. 도입하더라도 "같은 채널 최근 N개 릴리스"로 제한하고 전체 객체 폴백을 반드시 유지한다 |
| FastCDC는 1 GB/s/코어급 롤링 해시로 가변 청크를 만들어, 파일 앞부분에 1바이트가 삽입돼도 뒤쪽 청크가 유지된다. Riot은 이 방식으로 청크의 약 10%를 중복 제거했다 | v3 후보. 대용량 단일 파일(수백 MB 이상)이 실제로 문제가 될 때만 도입한다. v1의 파일 단위 구조 위에 "큰 파일만 청킹"으로 얹을 수 있게 매니페스트 스키마에 확장 여지를 남긴다 |

### 결정이 필요한 항목

1. **서명 알고리즘** — Ed25519 순수 관리 구현 / ECDSA P-256 / RSA-2048 중 무엇으로 할지. Unity IL2CPP 실기기 검증 결과에 따라 확정한다.
2. **스토리지 타깃** — S3 호환을 1순위로 잡을지, GCS·Azure·일반 HTTPS 업로드까지 v1에 넣을지. 기본안은 "S3 호환 1순위 + 업로더 인터페이스 추상화"다.
3. **로케일·플랫폼 분기 필요 여부** — 매니페스트에 필드는 넣되, 실제 필터링 기능을 v1에 넣을지 v2로 미룰지.
4. **선택(optional) 패키지 온디맨드 설치** — v1 필수인지. 게임 초기 다운로드 크기 요구에 따라 달라진다.
5. **클라이언트 설치 상태 저장소** — 저널 + JSON으로 시작하는 기본안을 유지할지, 파일 수가 수십만 규모라면 처음부터 SQLite를 검토할지.
