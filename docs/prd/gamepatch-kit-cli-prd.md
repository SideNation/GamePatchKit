# GamePatchKit CLI 패치 데이터 빌드

## 목적

게임 데이터 폴더를 읽어 배포용 패치 데이터(아카이브·파일 객체·매니페스트 JSON)를 만드는 CLI를 구현한다.

폴더를 하나의 아카이브로 묶어 배포하되, 그 안의 파일이 바뀌면 아카이브를 다시 만들지 않고 바뀐 파일만 별도 객체로 추가한다. 클라이언트는 기존 아카이브에 바뀐 파일을 덮어 받으므로 재배포량이 변경분만큼으로 줄어든다.

변경 여부는 git이 알려주고, 식별은 해시가 아닌 버전 번호로 한다.

## 개발 환경

| 항목 | 버전 |
| --- | --- |
| .NET | net10.0 (SDK 10.0.302) |
| NativeCompressions.Zstandard.Core | 0.6.1 |
| NativeCompressions.Zstandard.Runtime.win-x64 / .linux-x64 / .osx-arm64 | 0.6.1 |
| Newtonsoft.Json | 13.0.2 |
| YamlDotNet | 18.1.0 |

- 실행 환경은 `win-x64`, `linux-x64`, `osx-arm64` 세 가지다. 메타 패키지 `NativeCompressions.Zstandard`는 android·ios 네이티브까지 끌어오므로 참조하지 않고, `Core`와 위 세 RID 런타임 패키지만 개별 참조한다.
- 프로젝트는 `src/GamePatchKit.Cli`에 두고 실행 파일 이름은 `gpk`로 한다.
- 데이터 루트는 git 저장소의 최상위 폴더이거나 그 하위 폴더여야 한다. 변경 감지를 git에 의존한다.
- CLI는 nuget.org의 `GamePatchKit.Cli` 패키지로 배포하는 framework-dependent .NET tool이며, 설치 후 명령 이름은 `gpk`다. 실행 환경에는 .NET 10 런타임이 있어야 한다.

## 요구사항

### 명령

```
gpk build  --source <데이터 루트> --output <패치 데이터 폴더>
gpk verify --output <패치 데이터 폴더>
```

- `--source`를 생략하면 현재 폴더를 쓴다.
- `--output`은 `--source`가 속한 git 저장소 바깥의 폴더여야 한다. 저장소 내부 경로를 지정하면 빌드를 중단한다.
- `verify`는 `--output`만 받는다. 매니페스트가 산출물 이름·크기·checksum을 모두 담고 있어 자기서술적이고, 검증이 필요한 자리(배포 직전, 스토리지 이전 후, 백업 복원 후)에는 소스 체크아웃이 없기 때문이다.
- 재빌드 플래그는 두지 않는다. 그룹을 다시 빌드하는 방법은 yaml의 그룹 버전을 이전 성공 버전보다 올리는 것뿐이다. 같은 버전으로 내용만 다시 만들면 이미 받아간 클라이언트가 변경을 알 수 없기 때문이다.

### CLI 배포

- `GamePatchKit.Cli.csproj`는 `PackAsTool`을 사용하고 `ToolCommandName`은 `gpk`로 지정한다.
- NuGet 패키지는 `net10.0` framework-dependent 도구 하나로 만든다. self-contained, single-file, RID별 도구 패키지는 만들지 않는다.
- GitHub Actions는 `windows-latest`(`win-x64`), `ubuntu-latest`(`linux-x64`), `macos-26`(`osx-arm64`) 매트릭스에서 restore, test, pack, 로컬 tool 설치, zstd smoke run을 수행한다.
- GitHub Release가 게시되면 모든 매트릭스 검증이 성공한 뒤 release tag의 `v`를 제외한 값을 패키지 버전으로 사용해 nuget.org에 게시한다.
- NuGet API 키는 GitHub Actions secret `NUGET_API_KEY`로 전달한다. 패키지는 `artifacts` 폴더에 만들고, 같은 버전이 이미 있으면 건너뛴다.

### 버전 체계

| 구분 | 관리 주체 | 규칙 |
| --- | --- | --- |
| 그룹 버전 | 사용자 (yaml) | 0 이상의 정수. 이전 성공 버전과 같으면 증분 빌드하고, 더 크면 그룹 전체를 다시 빌드하며, 더 작으면 중단한다 |
| 파일 리비전 | CLI | 정수. 0에서 시작하고, 그 파일이 바뀔 때마다 1씩 올린다 |
| 파일 버전 | CLI | `<그룹 버전>.<파일 리비전>` 형식의 문자열 |

- 그룹 버전이 1이고 파일 리비전이 0이면 파일 버전은 `1.0`이다. 그 파일이 바뀌면 `1.1`이 된다.
- 이전 성공 버전은 현재 `manifest.json`에 같은 `id`로 기록된 그룹 버전이다. 이전 매니페스트에 해당 그룹이 없으면 신규 그룹으로 보며, output에 남아 있는 과거 산출물과의 충돌은 산출물 공통 쓰기 규칙으로 처리한다.
- 그룹 버전을 올리면 그룹 전체를 다시 빌드하고 새 파일 리비전은 0에서 시작한다. 다만 같은 파일 객체 경로 계열에 과거 산출물이 남아 있으면 아래 공통 쓰기 규칙에 따라 파일 리비전만 더 큰 값이 될 수 있다.
- 파일 버전은 매니페스트에 기록하고, 다음 빌드에서 이전 매니페스트를 읽어 이어받는다.

### 그룹 설정

`--source` 루트에 Git이 추적하는 `gamepatchkit.yml` 하나만 두고 그룹을 리스트로 나열한다. yaml이 추적되지 않으면 빌드를 중단한다. yaml은 CLI 입력에서만 쓰고 출력물에 포함하지 않는다.

```yaml
groups:
  - id: group1
    version: 1
    packing: group
    compression: zstd
  - id: group2
    version: 1
    packing: file
    compression: none
```

| 키 | 값 | 기본값 | 의미 |
| --- | --- | --- | --- |
| `id` | 문자열 | 없음 (필수) | 그룹 식별자이자 `--source` 기준 그룹 폴더 상대 경로 |
| `version` | 정수 | 0 | 그룹 버전. 이전 성공 버전보다 올리면 그룹 전체를 다시 빌드하며 낮출 수 없다 |
| `packing` | `group` \| `file` | `group` | 그룹 전체를 아카이브 하나로 묶을지, 파일마다 객체를 낼지 |
| `compression` | `zstd` \| `none` | `zstd` | 압축할지 원본 그대로 낼지 |

- `id`는 폴더를 가리킨다. `group1`이면 `<source>/group1`, `data/maps`면 `<source>/data/maps`다.
- 그룹에 빌드 대상 엔트리가 하나도 없으면 빌드를 중단하고 yaml에서 그룹을 제거하도록 안내한다. `id` 오타로 폴더가 없는 경우와 그룹의 파일을 모두 지운 경우가 모두 여기에 해당한다.
- 폴더 존재 여부를 따로 검사하지 않는다. Git은 빈 디렉터리를 추적하지 않아 그룹의 파일을 모두 지우면 폴더도 함께 사라지고, 로컬에는 폴더가 남고 새로 체크아웃한 곳에는 없는 상태가 생긴다. 두 상태를 엔트리 수 하나로 판정해야 체크아웃 상태에 따라 결과가 달라지지 않는다.
- 더 이상 쓰지 않는 그룹은 yaml에서 빼서 관리한다. 빈 그룹을 매니페스트에 남기지 않는다.

### 그룹 탐색

- 루트 yaml의 `groups` 리스트가 그룹 목록이다. 리스트에 없는 폴더는 빌드 대상이 아니다.
- 파일은 자신을 포함하는 가장 깊은 그룹에 속한다. 어느 그룹에도 속하지 않는 파일은 빌드 대상이 아니다.
- `--source` 아래에서 git이 추적하는 파일만 빌드 대상이다. 추적하지 않는 파일은 변경 감지가 불가능하므로 제외하며 dirty 상태로도 보지 않는다.
- 엔트리는 그룹 루트 기준 상대 경로를 `/`로 정규화하고 ordinal 오름차순으로 정렬한다.

### 변경 감지

1. 이전 매니페스트에 기록된 커밋과 현재 `HEAD` 사이의 변경 경로를 git에서 가져온다.
2. 변경된 경로에 해당하는 엔트리의 리비전을 1 올린다. 나머지 엔트리는 이전 버전을 그대로 쓴다.
3. 이전 매니페스트에 없던 경로는 새 파일이며 리비전 0에서 시작한다.
4. 이전 매니페스트에 있었으나 지금 없는 경로는 매니페스트에서 뺀다.
5. `--source` 아래의 Git 추적 파일에 커밋되지 않은 변경이 있으면 빌드를 중단한다. 추적하지 않는 파일과 `--source` 바깥의 변경은 입력에 포함하지 않고 dirty 판정에서도 제외한다. 커밋되지 않은 추적 파일로 만든 패치 데이터에 커밋 ID를 기록하면 그 버전을 다시 만들어낼 수 없기 때문이다.
6. 빌드한 `HEAD` 커밋을 매니페스트에 기록한다.

### 이전 매니페스트

- `--output` 폴더에 `manifest.json`이 있으면 이전 매니페스트로 읽는다. 파일 버전과 아카이브 위치 정보를 여기서 이어받는다.
- 이전 매니페스트가 없으면 모든 그룹을 처음 빌드하는 것으로 본다.
- `manifest.json`은 모든 산출물 처리가 끝난 성공 경로에서만 기록한다. 같은 디렉터리의 임시 파일에 완전히 쓴 뒤 최종 경로로 원자적으로 교체하므로, 후보 작성이나 교체에 실패하면 기존 파일을 그대로 둔다.
- 빌드가 중간에 실패하면 `sourceCommit`은 마지막으로 성공한 빌드의 커밋으로 남고, 다음 빌드는 그 커밋부터 다시 변경을 계산한다. 실패한 빌드가 이미 쓴 산출물은 후보와 같으면 재사용하고, 파일 객체가 다르면 파일 리비전을 증가시킨다. 같은 그룹 버전의 아카이브가 후보와 다르면 중단하며 사용자가 yaml의 그룹 버전을 올린 뒤 재실행한다.
- 진행 상황을 별도 파일에 남기지 않는다. 실패 복구의 기준점은 `sourceCommit` 하나이며, 중간 상태를 저장하면 이 성질이 깨진다.

### 이전 매니페스트 검증

이전 `manifest.json`은 역직렬화 직후, 그룹 판단·git diff·산출물 쓰기 전에 검증한다. 아래 조건을 하나라도 위반하면 `이전 매니페스트가 올바르지 않습니다.`와 필드 경로·이유를 출력하고 중단하며 `--output`을 바꾸지 않는다.

1. 루트의 `schemaVersion`은 CLI가 지원하는 값이고, `releaseVersion`은 0 이상이며, `sourcePath`는 `.` 또는 정규화된 저장소 기준 상대 경로이고, `sourceCommit`은 빈 문자열이 아니며 `groups`는 존재해야 한다.
2. 그룹 `id`는 중복되지 않은 정규화 상대 경로이고, 그룹 `version`은 0 이상이며 `entries`가 존재해야 한다. 같은 그룹의 엔트리 `path`도 중복되지 않은 정규화 상대 경로여야 한다.
3. 아카이브와 파일 객체의 `checksum`은 64자리 소문자 hex이고 모든 크기·offset·length는 0 이상이어야 한다.
4. 모든 그룹의 `entries`는 비어 있지 않아야 한다. `packing: file` 그룹은 `archive`가 없어야 하고 모든 엔트리가 `source: file`이어야 한다. `packing: group`에서 `source: archive` 엔트리가 하나라도 있으면 `archive`가 있어야 한다.
5. `source: archive` 엔트리는 `offset`·`length`만 가져야 한다. `length`는 `size`와 같고 `offset + length`는 오버플로 없이 `archive.payloadSize` 이하여야 하며, path 정렬 순서의 archive 엔트리 구간은 단조 증가하고 서로 겹치지 않아야 한다.
6. `source: file` 엔트리는 `name`·`storedSize`·`checksum`만 가져야 한다.
7. 엔트리 `version`은 `<그룹 버전>.<0 이상의 리비전>` 형식이어야 한다.
8. 아카이브 `name`은 `archives/<그룹 id>/<그룹 버전>.gpka`, 파일 객체 `name`은 `files/<그룹 id>/<그룹 버전>/<엔트리 path>.v<엔트리 version>`과 정확히 같아야 한다. 두 경로는 `/` 구분자를 쓰는 `--output` 내부 상대 경로다.

유효한 이전 매니페스트라도 `sourcePath`가 현재 `--source`의 저장소 기준 경로와 다르면 다른 데이터 루트의 상태를 승계할 수 있으므로, `데이터 루트가 이전 빌드와 다릅니다.`라고 알리고 그룹 판단과 산출물 쓰기 전에 중단한다. 저장소 루트의 `sourcePath`는 `.`, 하위 source는 `/` 구분자를 쓰는 저장소 기준 상대 경로로 기록한다.

### 증분 빌드의 전제

증분 빌드는 이전 상태를 그대로 이어받는다. 아래 전제가 깨지면 빌드를 중단하고 이유를 알린다. 식별이 해시가 아니므로 전제가 깨졌을 때 다시 계산해서 복구할 수단이 없다.

전제 1과 3은 깨지면 이어받은 결과 자체가 틀린다. 전제 2는 결과는 맞지만 매니페스트가 가리키는 산출물이 사라진 상태이므로, output 폴더의 손상을 빌드 시점에 알리는 것이 목적이다. 성격이 달라 검사 비용도 다르게 잡는다.

이전 매니페스트와 `id`·`version`이 모두 같은 현재 그룹을 증분 대상으로 본다. 이전 매니페스트에 없는 그룹은 첫 빌드 대상이고, 같은 `id`의 yaml 버전이 이전 성공 버전보다 크면 전체 빌드 대상이다. yaml 버전이 이전 성공 버전보다 작으면 산출물을 쓰기 전에 중단하고 더 큰 버전을 사용하도록 안내한다. 그룹 버전은 사용자가 yaml에서 올리며 CLI가 자동으로 바꾸지 않는다.

1. **증분 대상 그룹이 있으면 이전 커밋 객체가 있어야 한다.** 증분 대상 그룹이 하나 이상일 때만 이전 매니페스트의 `sourceCommit`으로 git diff를 수행한다. 커밋 객체가 현재 저장소에 없으면 빌드를 중단하고 `이전 상태가 없습니다.`라고 알린다. 증분 대상 그룹이 없으면 커밋 객체 확인과 git diff를 생략하고 모든 현재 그룹을 전체 빌드한다.
2. **증분 대상 그룹이 승계할 산출물이 있고 크기가 맞아야 한다.** 해당 그룹의 이전 아카이브와 파일 객체를 존재 여부와 실제 크기 순서로 검사한다. 파일이 없거나 실제 크기가 이전 매니페스트의 `storedSize`와 다르면 산출물을 쓰기 전에 중단한다. 참조 산출물당 크기 조회 한 번이라 바이트를 읽지 않는다.
3. **`packing`과 `compression`이 그대로여야 한다.** 그룹 버전을 그대로 둔 채 둘 중 하나가 바뀌면 중단하고 그룹 버전을 올리도록 안내한다. 매니페스트의 `compression`은 그룹에 하나뿐이라 아카이브와 오버레이가 서로 다른 압축을 쓰는 상태를 표현할 수 없다.

승계 산출물의 SHA-256 재계산은 이 전제에 넣지 않고 `gpk verify`로 분리한다. 증분 빌드가 이전 상태에서 읽는 것은 `manifest.json` 하나이고 승계 산출물의 바이트는 빌드의 입력이 아니므로, 검사해도 새 매니페스트의 내용이 달라지지 않는다. 반면 비용은 변경량이 아니라 승계 산출물 총량에 비례하고, 크기가 같은 바이트 손상은 존재·크기 검사가 잡는 사고보다 훨씬 드물다. 전량 해시는 사용자가 필요할 때 `gpk verify`로 수행한다.

### 산출물 공통 쓰기 규칙

- 그룹 버전은 yaml의 값을 그대로 사용한다. CLI는 충돌을 피하기 위해 그룹 버전을 자동으로 바꾸지 않는다.
- 아카이브와 파일 객체는 최종 경로에 직접 쓰지 않는다. 같은 디렉터리의 임시 파일에 후보 바이트를 모두 쓰고 `storedSize`와 SHA-256을 계산한 뒤 최종 경로를 결정한다. 임시 파일 이름은 정식 산출물 이름 규칙과 겹치지 않으며 버전 탐색에서 제외하고, 게시·재사용·충돌 중단을 결정한 뒤 제거한다.
- 아카이브 대상 경로가 비어 있으면 후보를 게시한다. 기존 아카이브가 후보와 `storedSize`·SHA-256이 같으면 기존 파일을 재사용하고, 다르면 그룹 버전 충돌로 중단한다. 어느 경우에도 기존 아카이브를 덮어쓰지 않는다.
- 파일 객체의 요청 리비전은 기존 규칙대로 변경 파일은 이전 리비전 + 1, 신규 파일과 전체 빌드 파일은 0이다. 같은 그룹 버전·상대 경로의 정식 파일 객체 중 요청 리비전 이상의 가장 높은 리비전을 찾는다.
  - 해당 객체가 없으면 요청 리비전으로 게시한다.
  - 가장 높은 리비전의 객체가 후보와 `storedSize`·SHA-256이 같으면 그 객체와 리비전을 재사용한다.
  - 저장 바이트가 다르면 가장 높은 리비전 + 1로 후보를 게시한다.
- 자동 증가하는 것은 파일 리비전뿐이다. 기존 파일 객체는 덮어쓰지 않으며, 실제 버전이 요청 버전과 달라진 내역은 빌드 성공 요약의 마지막에 경고 한 묶음으로 출력한다.
- 저장 바이트 비교는 **같은 입력이 같은 산출물 바이트를 낸다**는 전제 위에 있다. zstd는 단일 스레드로 호출하고 압축 파라미터와 `NativeCompressions` 버전을 고정한다. 재사용·충돌 판정 전체가 이 전제에 의존하므로, CLI를 올려 zstd 라이브러리 버전이 바뀌면 입력이 같아도 아카이브 후보 바이트가 달라져 그룹 버전 충돌로 중단될 수 있다. 이때는 사용자가 그룹 버전을 올려 해소한다.
- 저장된 산출물의 크기와 SHA-256은 파일을 통째로 메모리에 올리지 않고 스트림에서 계산한다. 아카이브는 2 GB를 넘을 수 있어 전체 적재 방식으로는 계산 자체가 실패한다.

### `packing: group` — 그룹을 새로 빌드하는 경우

첫 빌드이거나, yaml의 그룹 버전이 이전 성공 버전보다 클 때.

1. 정렬된 엔트리 순서로 파일 내용을 이어 붙여 payload를 만든다.
2. `compression: zstd`면 payload 전체를 zstd 1프레임으로 압축하고, `none`이면 그대로 둔다. 파일 경계를 넘어 압축 윈도우가 이어져야 같은 폴더의 유사한 파일에서 압축률이 나오므로 엔트리별 개별 압축은 쓰지 않는다.
3. `archives/<그룹 id>/<그룹 버전>.gpka`로 저장한다.
4. 모든 엔트리는 파일 버전 `<그룹 버전>.0`을 갖고 payload 기준 offset과 length를 갖는다. offset은 정렬 순서대로 단조 증가해야 한다. 클라이언트가 스트림을 순차 해제하며 구간을 그대로 파일로 흘려 쓸 수 있어야 하기 때문이다.
5. 이전 오버레이는 새 매니페스트가 참조하지 않는다.
6. 아카이브 게시에는 공통 쓰기 규칙을 적용한다. 앞선 빌드가 같은 아카이브만 쓴 뒤 실패했다면 재실행에서 재사용하고, 같은 그룹 버전의 다른 아카이브가 있으면 중단한다.

### `packing: group` — 그룹 버전이 그대로일 때

1. 아카이브 파일은 다시 만들지 않고 이전 매니페스트의 아카이브를 그대로 참조한다.
2. 엔트리마다 변경 감지 결과를 본다.
   - 바뀌지 않았으면 이전 엔트리의 버전과 위치 정보를 그대로 승계한다. 아카이브 안이면 offset·length, 오버레이면 그 객체 경로다.
   - 바뀌었거나 새로 생긴 파일이면 요청 리비전을 계산한 뒤 공통 쓰기 규칙으로 실제 파일 리비전을 정하고, 그룹의 `compression` 설정대로 `files/<그룹 id>/<그룹 버전>/<상대 경로>.v<파일 버전>`에 저장해 오버레이로 기록한다.
   - 사라진 경로는 매니페스트에 싣지 않는다. 아카이브 안의 해당 구간은 남지만 아무도 참조하지 않는다.
3. 아카이브의 offset·length는 아카이브를 만든 시점에 고정된다. 오버레이가 쌓여 아카이브에 죽은 구간이 늘어나면 사용자가 yaml의 그룹 버전을 올려 회수한다.

### `packing: file`

1. 엔트리마다 `compression` 설정대로 압축하거나 원본 그대로 `files/<그룹 id>/<그룹 버전>/<상대 경로>.v<파일 버전>`에 저장한다.
2. 아카이브를 만들지 않는다. 모든 엔트리의 `source`는 `file`이다.
3. 그룹 버전이 이전 성공 버전보다 크면 모든 엔트리의 요청 버전을 `<그룹 버전>.0`으로 정한다. 그대로면 바뀐 파일만 이전 리비전 + 1을 요청한다. 실제 파일 리비전은 공통 쓰기 규칙으로 확정한다.
4. `packing: file` 그룹의 버전을 올리면 바뀌지 않은 파일까지 전부 새 세대 폴더에 다시 쓰이고 클라이언트는 그룹 전체를 다시 받는다. 회수할 아카이브 죽은 구간이 없어 재패키징 이득은 없고 비용만 남으므로, `packing`이나 `compression`을 바꿀 때만 올린다.

### 출력 레이아웃

```
<output>/
  manifest.json
  archives/<그룹 id>/<그룹 버전>.gpka
  files/<그룹 id>/<그룹 버전>/<그룹 루트 기준 상대 경로>.v<파일 버전>
```

- 그룹 버전으로 폴더를 나눈다. 그룹 버전을 올리면 그 세대의 파일 객체가 새 폴더에 쌓이므로, 더 이상 쓰지 않는 세대를 폴더 단위로 통째로 지울 수 있다.
- 그 폴더 안에서는 원본 폴더 구조를 그대로 유지하고, 파일 이름 **뒤에** `.v<파일 버전>`을 붙인다. `data/maps/desert.json`은 `files/<그룹 id>/1/data/maps/desert.json.v1.2`가 된다.
- 확장자를 앞뒤로 쪼개는 규칙을 두지 않으므로 `.tar.gz`나 확장자 없는 파일도 같은 규칙으로 처리된다.
- 구분자는 `.v`다. 쓰이는 문자가 `.`과 `v`뿐이라 RFC 3986 unreserved 집합과 S3 객체 키 safe 문자 집합에 모두 들어간다. `@`는 파일 시스템에서는 문제가 없지만 S3 문서가 "특별 처리가 필요한 문자"로 지정하고 있어 쓰지 않는다.
- 같은 파일의 여러 리비전이 한 폴더에 나란히 놓인다. 리비전마다 폴더를 만들지 않으므로 파일 하나만 바뀐 패치에서 폴더가 늘어나지 않는다.

### 매니페스트

`schemaVersion`은 정수 `1`로 시작한다.

| 영역 | 필드 |
| --- | --- |
| 루트 | `schemaVersion`, `releaseVersion`, `sourcePath`, `sourceCommit`, `groups` |
| 그룹 | `id`, `version`, `packing`, `compression`, `archive`(있을 때), `entries` |
| 아카이브 | `name`, `payloadSize`, `storedSize`, `checksum` |
| 엔트리 | `path`, `version`, `size`, `source`(`archive` \| `file`) |
| `source: archive` | `offset`, `length` |
| `source: file` | `name`, `storedSize`, `checksum` |

- `releaseVersion`은 매니페스트 전체의 세대를 가리키는 0 이상의 정수다. 첫 빌드는 0이고, 이후에는 `releaseVersion`을 제외한 매니페스트 내용이 이전 성공 매니페스트와 다를 때 CLI가 이전 값보다 1 증가시킨다. 그룹 버전과 달리 사용자가 결정할 것이 없으므로 CLI가 정한다.
- `releaseVersion`을 제외한 새 매니페스트 내용이 이전 성공 매니페스트와 같으면 이전 값을 그대로 쓴다. 아무것도 바꾸지 않고 다시 빌드했을 때 매니페스트가 이전과 같아야 하는 완료 조건 4를 지키기 위해서다.
- 이미 게시된 패치 데이터의 지정 수동 배포 환경은 [업로드 PRD](gamepatch-kit-cli-upload-prd.md)의 별도 private 상태 Git 저장소에서 이전 `manifest.json`을 복원한다. 이전 매니페스트가 없는 상태는 실제 첫 배포에만 허용하며, CLI 자체는 원격 상태를 조회해 상태 유실과 첫 배포를 구분하지 않는다.
- 매니페스트가 자기 세대를 담으므로 파일 하나만 가진 쪽도 그것이 어느 세대인지 안다. 배포된 매니페스트를 세대별로 보관하고 소비자가 세대를 골라 받는 방식은 [gamepatch-kit-distribution-prd.md](gamepatch-kit-distribution-prd.md)에서 다룬다.
- 그룹은 `id` 오름차순, 엔트리는 `path` 오름차순으로 쓴다.
- 필드 이름은 `[JsonProperty]`로 고정한다. Unity 클라이언트가 같은 모델을 읽게 되므로 이름 자동 추론에 기대지 않는다.
- `manifest.json`은 `Formatting.None`, UTF-8 BOM 없음, 끝 개행 없음으로 쓴다. 들여쓰기를 켜면 Newtonsoft가 줄바꿈에 `Environment.NewLine`을 써서 운영체제마다 바이트가 달라지고, 완료 조건 4의 매니페스트 바이트 동일성이 깨진다.
- `source: archive` 엔트리의 `length`는 payload가 무압축 연결이므로 항상 `size`와 같다. 의도한 중복이며, 매니페스트만 읽는 쪽이 아카이브 구간 길이를 원본 크기와 별개의 값으로 다룰 수 있게 남긴다.
- `checksum`은 저장된 산출물 바이트 그대로의 SHA-256(소문자 hex)이다. 아카이브는 `.gpka` 파일 전체, 파일 객체는 저장된 객체 파일 전체가 대상이다. 전송받는 단위마다 하나씩이므로 클라이언트가 내려받은 바이트가 잘리거나 손상되지 않았는지 이것으로 확인하고, 배포하는 쪽에서는 `gpk verify`가 같은 값으로 저장된 산출물을 확인한다. 손상 감지용이지 위조 방지가 아니다. SHA-256은 .NET 내장이라 새 의존성이 없다.

### 빌드 요약 출력

그룹마다 엔트리 수, 그룹 버전, 아카이브를 새로 만들었는지 여부, 새로 쓴 파일 객체 수, 새로 쓴 총 바이트를 출력하고 합계를 낸다. 파일 리비전을 자동 증가시킨 항목이 있으면 모든 정상 요약 뒤에 경고 한 묶음으로 그룹 id, 상대 경로, 요청 버전, 실제 버전을 출력한다. 자동 증가 항목이 없으면 경고를 출력하지 않는다.

### 산출물 검증

```
gpk verify --output <패치 데이터 폴더>
```

`--output`의 `manifest.json`이 가리키는 산출물이 실제로 그대로 있는지 확인한다. 빌드하지 않고 산출물을 바꾸지 않는다.

1. `manifest.json`을 읽고 위 "이전 매니페스트 검증"과 같은 관계 검증을 수행한다.
2. 매니페스트가 참조하는 모든 산출물을 검사한다. 그룹마다 `archive`(있으면)와 모든 `source: file` 엔트리의 객체다. `source: archive` 엔트리는 아카이브 안에 있으므로 아카이브 검사로 함께 확인된다.
3. 각 산출물을 존재 여부 → 실제 크기 대 `storedSize` → SHA-256 대 `checksum` 순서로 검사한다. 크기가 다르면 SHA-256을 계산하지 않는다.
4. 첫 실패에서 멈추지 않고 모든 불일치를 경로와 이유로 나열한다. 손상된 저장소는 한 건이 아니라 목록이 필요하다.
5. 하나라도 불일치하면 0이 아닌 종료 코드로 끝낸다.

- `--source`, git 저장소, `gamepatchkit.yml`을 요구하지 않는다.
- 매니페스트가 참조하지 않는 파일은 보지 않는다. 미참조 객체 보고와 정리는 제외 범위다.
- 아카이브를 해제해 offset·length를 다시 확인하지 않는다. SHA-256이 저장 바이트 전체를 이미 고정했고 구간 정합성은 관계 검증이 본다.
- 손상을 고치지 않는다. 버전으로 식별하므로 지난 세대의 산출물을 다시 만들어낼 수단이 없고, 대응은 그룹 버전을 올려 다시 배포하는 것뿐이다.

## 예시

`group1`을 시간 순으로 따라간다. 이어서 `packing: file` 그룹을 본다.

### 1. 최초 빌드

**입력**

```
source/
  gamepatchkit.yml
  group1/
    file1.json           120 B
    file2.json           80 B
```

```yaml
groups:
  - id: group1
    version: 1
    packing: group
    compression: zstd
```

**출력**

```
output/
  archives/group1/1.gpka      payload 200 B → 압축 90 B
  manifest.json
```

**매니페스트**

| path | version | source | 위치 |
| --- | --- | --- | --- |
| `file1.json` | `1.0` | archive | offset 0, length 120 |
| `file2.json` | `1.0` | archive | offset 120, length 80 |

클라이언트는 `archives/group1/1.gpka` 하나만 받는다.

### 2. `file1.json` 변경

파일을 고치고 커밋한 뒤 다시 빌드한다. git이 `file1.json` 변경을 알려준다.

**출력에 추가되는 것**

```
files/group1/1/file1.json.v1.1      140 B → 압축 70 B
```

아카이브는 다시 만들지 않는다.

**매니페스트**

| path | version | source | 위치 |
| --- | --- | --- | --- |
| `file1.json` | `1.1` | file | `files/group1/1/file1.json.v1.1` |
| `file2.json` | `1.0` | archive | offset 120, length 80 |

- 새로 설치하는 클라이언트: `archives/group1/1.gpka` + `files/group1/1/file1.json.v1.1`
- 아카이브를 이미 가진 클라이언트: `files/group1/1/file1.json.v1.1`만

### 3. `file1.json` 다시 변경

**출력에 추가되는 것**

```
files/group1/1/file1.json.v1.2
```

`file1.json`의 버전은 `1.2`가 된다. `files/group1/1/file1.json.v1.1`은 파일로 남지만 새 매니페스트가 참조하지 않는다.

### 4. `file3.json` 추가

새 파일은 아카이브에 들어갈 수 없으므로 리비전 0에서 시작하는 오버레이가 된다.

**출력에 추가되는 것**

```
files/group1/1/file3.json.v1.0
```

**매니페스트**

| path | version | source | 위치 |
| --- | --- | --- | --- |
| `file1.json` | `1.2` | file | `files/group1/1/file1.json.v1.2` |
| `file2.json` | `1.0` | archive | offset 120, length 80 |
| `file3.json` | `1.0` | file | `files/group1/1/file3.json.v1.0` |

### 5. `file2.json` 삭제

매니페스트에서 빠진다. 아카이브의 offset 120~200 구간은 남지만 아무도 참조하지 않는다.

| path | version | source | 위치 |
| --- | --- | --- | --- |
| `file1.json` | `1.2` | file | `files/group1/1/file1.json.v1.2` |
| `file3.json` | `1.0` | file | `files/group1/1/file3.json.v1.0` |

이 시점에서 아카이브는 대부분 죽은 구간이고 실제 데이터는 오버레이에 있다.

### 6. 그룹 버전 올림 — 재패키징

루트 `gamepatchkit.yml`에서 `group1`의 `version`을 1에서 2로 바꾸고 빌드한다.

**출력에 추가되는 것**

```
archives/group1/2.gpka      file1.json + file3.json 을 이어 붙여 압축
```

**매니페스트**

| path | version | source | 위치 |
| --- | --- | --- | --- |
| `file1.json` | `2.0` | archive | offset 0, length 140 |
| `file3.json` | `2.0` | archive | offset 140, length 60 |

모든 리비전이 0으로 돌아가고 오버레이가 사라진다. 이전 `archives/group1/1.gpka`와 `files/group1/1/*`는 파일로 남지만 새 매니페스트가 참조하지 않는다.

### 7. `packing: file` 그룹

**입력**

```
source/
  gamepatchkit.yml
  group2/
    a.bin
    b.bin
```

```yaml
groups:
  - id: group2
    version: 1
    packing: file
    compression: none
```

**최초 빌드 출력**

```
files/group2/1/a.bin.v1.0
files/group2/1/b.bin.v1.0
```

아카이브를 만들지 않고, 두 엔트리 모두 `source: file`에 버전 `1.0`이다.

**`b.bin`만 변경 후 빌드**

```
files/group2/1/b.bin.v1.1
```

`a.bin`은 `1.0` 그대로 두고 `b.bin`만 `1.1`로 다시 낸다.

## 완료 조건

1. `packing: group` 그룹을 처음 빌드하면 `archives/<id>/<그룹 버전>.gpka` 하나가 생기고, 모든 엔트리가 `source: archive`이며 버전이 `<그룹 버전>.0`이다.
2. 아카이브를 매니페스트의 offset·length로 잘라낸 결과가 원본 파일과 바이트 단위로 같다.
3. 파일 하나를 고쳐 커밋하고 다시 빌드하면 아카이브는 새로 만들어지지 않고, 그 파일의 리비전만 1 올라간 오버레이 하나가 생긴다. 나머지 엔트리는 이전 버전과 위치를 유지한다.
4. 아무것도 바꾸지 않고 다시 빌드하면 새 파일이 하나도 생기지 않고 매니페스트 내용이 이전과 같다.
5. `packing: group` 그룹의 yaml 버전을 이전 성공 버전보다 올리고 빌드하면 새 아카이브가 생기고 모든 엔트리가 `source: archive`에 리비전 0으로 돌아간다. yaml 버전을 이전 성공 버전보다 낮추면 산출물과 매니페스트를 바꾸지 않고 중단한다.
6. `packing: file` 그룹에서 파일 하나만 고치면 그 파일의 객체만 새로 생긴다.
7. 그룹에서 파일을 지우고 빌드하면 해당 엔트리가 매니페스트에서 빠지고 나머지 엔트리는 그대로 동작한다.
8. 그룹에 파일을 추가하고 해당 경로의 기존 파일 객체가 없으면 리비전 0인 오버레이로 들어간다.
9. `--source` 아래의 Git 추적 파일에 커밋되지 않은 변경이 있으면 빌드가 중단되고 이유를 알린다. 추적하지 않는 파일과 `--source` 바깥의 변경은 빌드 입력과 dirty 판정에서 제외된다.
10. 매니페스트에 현재 `--source`의 저장소 기준 `sourcePath`와 빌드한 커밋이 기록되고, 다음 빌드가 같은 source인지 확인한 뒤 그 커밋을 기준으로 변경을 판정한다. 다른 source로 같은 output을 사용하면 산출물과 매니페스트를 바꾸지 않고 중단한다.
11. `compression: none` 그룹의 산출물이 원본 바이트와 같다.
12. 매니페스트의 `checksum`이 해당 아카이브·파일 객체의 실제 바이트를 SHA-256으로 해시한 값과 일치한다.
13. GitHub Actions의 `win-x64`, `linux-x64`, `osx-arm64` 대응 러너에서 NuGet .NET tool 패키지를 설치하고 `gpk build`를 실행할 수 있다. GitHub Release 게시 시 세 환경의 검증을 모두 통과한 동일 버전의 `GamePatchKit.Cli` 패키지가 nuget.org에 게시된다.
14. `packing`이나 `compression`을 바꾸면서 그룹 버전을 그대로 두면 빌드가 중단되고 그룹 버전을 올리라는 안내가 나온다.
15. 그룹의 빌드 대상 엔트리가 하나도 없으면 빌드가 중단되고 yaml에서 그룹을 제거하라는 안내가 나오며 산출물과 매니페스트가 바뀌지 않는다. 그룹의 파일을 모두 지워 폴더까지 사라진 경우와 `id`에 오타가 있어 폴더가 없는 경우가 같은 결과를 낸다.
16. 이전 매니페스트와 `id`·`version`이 같은 그룹이 하나 이상일 때만 이전 `sourceCommit` 커밋 객체와 해당 그룹이 승계할 모든 산출물의 존재 여부·`storedSize`를 확인한다. 커밋 객체가 없거나 승계 산출물이 없거나 실제 크기가 이전 매니페스트와 다르면 빌드가 중단되고 산출물과 매니페스트가 바뀌지 않는다. 크기가 같고 바이트만 다른 승계 산출물은 `build`가 검사하지 않으며 `gpk verify`가 담당한다. 모든 현재 그룹이 신규이거나 버전이 올라갔다면 이전 커밋 객체와 과거 산출물이 없어도 전체 빌드에 성공한다.
17. `--output`을 `--source`가 속한 git 저장소 내부로 지정하면 빌드가 중단되고 산출물이 생기지 않는다.
18. 아카이브 대상 경로에 후보와 저장 바이트가 같은 파일이 있으면 재사용해 빌드에 성공한다. 저장 바이트가 다르면 그룹 버전 충돌로 중단되고 기존 아카이브와 매니페스트가 바뀌지 않는다.
19. 파일 객체의 요청 리비전 이상인 마지막 객체가 후보와 같으면 그 버전을 재사용하고, 다르면 마지막 리비전 + 1로 새 객체를 만든다. 그룹 버전은 yaml과 동일하게 유지하며, 실제 버전이 요청 버전과 달라진 내역은 빌드 성공 요약 마지막에 한 번만 경고한다.
20. `manifest.json`은 같은 디렉터리의 임시 파일에서 완성한 뒤 원자적으로 교체하며, 실패한 빌드는 기존 매니페스트를 바꾸지 않는다. 재실행은 마지막 성공 `sourceCommit`부터 변경을 다시 계산한다. 실패한 빌드가 쓴 산출물과 후보가 같으면 재사용하고, 파일 객체가 다르면 파일 리비전을 증가시킨다. 같은 그룹 버전의 아카이브가 다르면 중단하고, 사용자가 그룹 버전을 올려 재실행하면 해당 그룹은 현재 `HEAD`로 전체 빌드되며 다른 증분 그룹도 실패 구간의 변경을 포함한다.
21. 이전 매니페스트가 JSON으로 읽히더라도 잘못된 `sourcePath`, 중복 그룹·엔트리, 잘못된 상대 경로·버전·checksum·조건부 필드, 음수 크기, 아카이브 범위를 벗어나거나 겹치는 구간 중 하나가 있으면 그룹 판단과 산출물 쓰기 전에 중단하고 `--output`을 바꾸지 않는다.
22. `gpk verify --output <폴더>`가 매니페스트의 모든 아카이브·파일 객체를 존재 여부·`storedSize`·SHA-256으로 검사한다. 모두 일치하면 종료 코드 0으로 끝나고, 산출물을 삭제하거나 truncate하거나 크기를 유지한 채 바이트를 바꾸면 해당 경로와 이유가 **모두** 나열되며 0이 아닌 종료 코드로 끝난다. `--source`와 git 저장소와 `gamepatchkit.yml` 없이 실행되고 산출물과 매니페스트를 바꾸지 않는다.
23. 첫 빌드의 `releaseVersion`은 0이고, `releaseVersion`을 제외한 매니페스트 내용이 이전 성공 매니페스트와 달라질 때마다 이전 값보다 1 증가한다. 내용이 같으면 값이 유지되어 매니페스트 바이트가 이전과 같다.

## 제외 범위

사용자가 이번 범위를 패치 데이터 생성 과정으로 한정했다. 다음은 넣지 않는다.

- CDN·캐시 정책, 채널·롤아웃. 패치 산출물 업로드는 [gamepatch-kit-cli-upload-prd.md](gamepatch-kit-cli-upload-prd.md)에서 별도로 다룬다
- 클라이언트 런타임(다운로드·검증·적용·롤백)
- 서명·키 관리 — 매니페스트의 체크섬은 전송 손상 감지용이다. 위조 방지가 필요해지면 서명을 별도로 다룬다
- 미참조 객체 정리, 보존 정책
- Zstandard 사전, 델타 압축, 콘텐츠 정의 청킹
- 병렬 처리, 재시도
- 플랫폼·로케일 필터, 선택 패키지
- **ZLogger** — 이번 범위에서 필요한 출력은 빌드 요약뿐이라 로깅 프레임워크를 넣지 않는다.
- **그룹 버전 자동 증가** — 오버레이가 얼마나 쌓였을 때 재패키징이 이득인지는 정하지 않는다. 사용자가 yaml을 고쳐서 결정한다.
