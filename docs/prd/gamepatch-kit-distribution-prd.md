# GamePatchKit 패치 데이터 배포와 소비

## 목적

게시된 패치 데이터를 게임 서버와 클라이언트가 같은 규칙으로 받아 쓰게 한다.

서버도 클라이언트도 데이터를 소비한다. 서버는 게임 로직에, 클라이언트는 표시에 쓴다. 둘은 서로를 기다리지 않으며 데이터 버전이 항상 같을 필요도 없다. 정합성을 맞추는 대신, 클라이언트가 자기가 붙은 서버의 버전을 따라가게 해서 한 세션 안에서만 일치시킨다.

## 개발 환경

| 항목 | 용도 |
| --- | --- |
| Supabase Storage 공개 버킷 | 매니페스트와 산출물 |
| Supabase Postgres | 릴리스 버전 포인터 |
| Newtonsoft.Json 13.0.2 | 매니페스트 파싱. 서버와 Unity 클라이언트가 같은 모델을 쓴다 |

- 게임 데이터는 공개돼도 되므로 버킷을 공개로 둔다. 클라이언트가 키 없이 받는다.
- 소비 측 읽기 로직은 서버(.NET)와 Unity 클라이언트가 공유한다. CLI는 쓰기, 소비 측은 읽기다.

## 게시 측 전제

이 문서는 아래를 전제하며, 셋 다 게시 측 PRD에 반영돼 있다.

| 전제 | 위치 |

| `gpk upload`가 게시한 릴리스 버전을 출력한다 | 같은 문서 업로드 요약, 완료 조건 15 |

## 요구사항

### 릴리스 버전

- 0 이상의 단조 증가 정수다. 매니페스트 루트의 `releaseVersion`에 기록한다.
- `gpk build`가 이전 매니페스트의 값 + 1로 정한다. 그룹 버전과 달리 사용자가 결정할 것이 없어 CLI가 올린다.
- 새 매니페스트가 `releaseVersion`을 뺀 나머지에서 이전과 같으면 값을 유지한다. 아무것도 바꾸지 않고 다시 빌드하면 매니페스트가 이전과 같아야 한다는 기존 규칙을 깨지 않기 위해서다.
- 매니페스트가 자기 버전을 담으므로 소비자는 파일 하나만 갖고도 자기가 어느 세대인지 안다.

### 매니페스트 게시

- 각 세대는 `manifests/<releaseVersion>.json`에 게시하고 덮어쓰지 않는다. 다른 산출물과 같은 규칙이다.
- 소비자는 이 경로만 읽는다. 받는 도중에 내용이 바뀌지 않고, 지난 세대를 그대로 다시 받을 수 있다.

### 버전 포인터

- 현재 릴리스 버전을 Postgres 테이블 한 줄에 둔다. 소비자가 감시하는 유일한 가변 값이다.
- `gpk upload`가 성공한 뒤 CI가 갱신한다. CLI는 Postgres를 건드리지 않는다.
- 롤백은 포인터에 이전 값을 쓰는 것이다. 산출물과 매니페스트가 불변이라 되돌릴 대상이 그대로 남아 있다.

### 게시 순서

```
1. 산출물 업로드
2. manifests/<N>.json 업로드
3. 포인터에 N 기록          ← 마지막
```

**포인터가 N이면 `manifests/<N>.json`과 그것이 참조하는 모든 산출물이 이미 올라가 있다.** 이 성질이 소비 측 전체의 전제다. 중간에 실패하면 포인터는 이전 값을 가리킨 채 남고 소비자는 아무 영향을 받지 않는다.

### 산출물 주소

```
https://<project>.supabase.co/storage/v1/object/public/<bucket>/<매니페스트의 name>
```

매니페스트의 `name`이 이미 `/` 구분자의 상대 경로이므로 그대로 이어 붙인다. 소비자가 알아야 하는 것은 URL prefix 하나뿐이다.

### 서버

1. 포인터를 감시한다. Realtime 구독이나 주기적 조회 중 하나를 쓴다.
2. 값이 바뀌면 `manifests/<N>.json`을 받는다.
3. 지금 쓰고 있는 매니페스트와 비교해 **새 매니페스트에만 있는 `name`을 받는다.** 이전 세대에서 바뀌지 않은 아카이브와 파일 객체는 다시 받지 않는다.
4. 새 세대를 완전히 로드한 뒤 참조를 원자적으로 교체한다. 요청 처리 도중에 데이터가 바뀌지 않아야 한다.
5. 받거나 로드하는 데 실패하면 이전 세대로 계속 서빙한다. 포인터를 되돌리거나 다른 서버에 알리지 않는다.
6. 자기가 로드한 버전을 클라이언트에 알린다. 전달 경로는 기존 서버·클라이언트 프로토콜을 쓴다.

서버끼리 버전을 맞추지 않는다. 한 서버가 못 받아도 나머지는 진행하며, 서버마다 버전이 다른 기간이 생기는 것을 허용한다.

### 클라이언트

1. **서버가 알려준 버전을 쓴다.** 포인터를 직접 보지 않는다.
2. 올라가는 것과 내려가는 것을 같게 처리한다. 서버마다 버전이 다를 수 있어 접속한 서버가 이전 세대일 수 있고, 지난 세대의 매니페스트가 불변으로 남아 있어 특별한 처리가 필요 없다.
3. 서버와 같은 방식으로 델타만 받는다.
4. 공개 URL로 직접 받는다. 서버를 거치지 않는다.

### 데이터 복원

매니페스트를 받은 소비자는 다음 순서로 파일 트리를 만든다. 서버와 클라이언트가 같은 구현을 쓴다.

1. `packing: group` 그룹은 `archive`를 받아 `compression`대로 해제하고, 각 `source: archive` 엔트리를 `offset`·`length`로 잘라낸다.
2. `source: file` 엔트리는 해당 객체를 받아 `compression`대로 해제한다.
3. 같은 `path`에 아카이브 구간과 파일 객체가 함께 오지 않는다. 매니페스트가 엔트리마다 `source`를 하나만 갖는다.

## 완료 조건

1. 포인터가 N이면 `manifests/<N>.json`과 그 매니페스트가 참조하는 모든 산출물을 공개 URL로 인증 없이 받을 수 있다.
2. 새 세대를 게시하는 중에도 이전 세대의 `manifests/<N-1>.json`과 그 산출물이 그대로 받아진다.
3. 포인터를 N-1로 되돌리면 서버가 N-1로 돌아가고, 그 서버에 붙은 클라이언트도 N-1을 쓴다.
4. 서버가 N을 받거나 로드하는 데 실패하면 이전 세대로 계속 서빙하고 클라이언트가 받는 버전도 바뀌지 않는다.
5. 서버 A가 N, 서버 B가 N-1인 상태에서 각 서버에 붙은 클라이언트가 각각 N과 N-1을 쓰며, 어느 쪽도 오류로 처리하지 않는다.
6. 이전 세대를 가진 소비자가 새 세대로 갈 때 바뀌지 않은 아카이브와 파일 객체를 다시 받지 않는다.
7. 다운로드 도중 새 세대가 게시돼도 진행 중인 다운로드가 두 세대에 걸치지 않는다.
8. 서버가 세대를 교체하는 동안 처리 중이던 요청이 한 세대의 데이터만 본다.
9. 소비자가 아카이브를 `offset`·`length`로 잘라낸 결과가 원본 파일과 바이트 단위로 같다.
10. 매니페스트만 갖고도 그것이 어느 릴리스 버전인지 알 수 있다.

## 제외 범위

- **서버 간 데이터 버전 정합성** — 서버마다 버전이 다른 기간을 허용한다. 맞추기 위한 배리어, 헬스체크 연동, 조율 장치를 만들지 않는다
- 클라이언트 강제 업데이트, 최소 지원 버전 강제
- 서버가 클라이언트에 버전을 알리는 전달 경로 — 기존 서버·클라이언트 프로토콜을 쓴다
- 다운로드 재시도, 백오프, `Range`를 이용한 중단 지점 재개
- 소비 측 캐시 저장 위치와 축출 정책
- **지난 세대 정리와 보존 정책** — 세대는 계속 쌓이며 이 문서는 지우는 시점을 정하지 않는다. 필요할 때 사용자가 직접 지운다. 지운 세대에 머물러 있던 소비자는 그 세대를 더 받을 수 없다
- 서명 URL, 접근 제어, 버킷 비공개 전환 — 게임 데이터가 공개돼도 되므로 공개 버킷을 쓴다
- 채널, A/B, 점진 배포
- 서버 구현 프레임워크와 Unity 통합 방식
